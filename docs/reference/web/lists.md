# Lists: add a list screen

How to put a list on the list standard ([ADR-0007](../../adr/0007-list-standard.md), spec [#547](https://github.com/kzndotsh/watchdog/issues/547)). The machinery is described in [`data.md`](data.md#declared-lists) (query, cache, URL) and [`ui/atoms.md`](ui/atoms.md#lists) (the parts); this page is the order to wire them in. The pilot screens are the models: the Identifiers table (`domains/entities/components/identifiers-page.tsx`), the Entities table (`domains/entities/components/entity-table.tsx`, whose rows carry their Connection counts from the server), the Dossier Identifiers tab (`domains/dossier/components/identifiers-section.tsx`, a table with a fixed filter) the Dossier Evidence tab (`domains/dossier/components/entity-evidence-section.tsx`, a queue body with a URL selection), Deleted Cases (`domains/cases/components/deleted-cases-view.tsx`, a queue body with row actions over a list that has no scope: the organization is the caller's) the Triage queue (`domains/triage/components/triage.tsx`, a split queue whose selection defaults to the first row and survives a filter that hides it) and the Tasks board (`domains/tasks/components/tasks-page.tsx`, two finished columns that are the Task list with `status` fixed, beside open columns that are one capped read of the same view). The `/ui` gallery's Lists section runs the same parts on in-memory data.

A screen holds no filter, search, sort or paging state of its own. If you are writing a `useState` for one, or filtering rows in the browser, stop: it belongs in the declaration or the URL.

## Steps

1. **The declaration and its binding.** The list exists in `@watchdog/schemas` (`defineList`), its SQL in `@watchdog/db` (`defineListRepo`) and its procedure takes `def.input` and returns `ListPage<T>`. If it does not, that is the server ticket first ([#548](https://github.com/kzndotsh/watchdog/issues/548) to [#550](https://github.com/kzndotsh/watchdog/issues/550) are the model).
2. **One page ServerFn** in the domain's `*.functions.ts`: `.validator(def.input)`, then pass `data` to the oRPC procedure whole (`listIdentifiersPageFn`, `listEvidencePageFn`). Never `listAllPages`. If the screen opens rows it may not have loaded (a URL selection), add a by-id ServerFn too (`getEvidenceFn` over `evidence.get`, or `getMany`: `getEvidenceManyFn`, `getEntitiesFn`).
3. **The view** in the domain's `queries.ts`: `listView(def, { domain, scopeKey, isScopeReady, fetchPage, getId, staleTime, gcTime })`. `domain` is the key root the domain's invalidation already names (`"identifiers"`, `"evidence"`), so SSE and mutations refresh every view with no new wiring. `fetchPage` spreads `params` and adds the scope ids and the cursor.
4. **The route's search.** A screen whose route is the list: `validateSearch` returns `ListSearch<typeof def>` from `def.searchWith({ ...routeOwnParams })`. `searchWith({})` outputs exactly `ListSearch<typeof def>`, so the schema itself is `validateSearch` (the Identifiers route). The loader warms the URL's first page (`view.warm(client, scope, def.queryOf(search))`) and `loaderDeps` stays empty, so typing and filtering never re-run it. The component passes `Route.useSearch()` and `usePatchSearch()` to the screen.
5. **The screen.** `useList(view, { scope, fixed?, search, onSearchChange })` is the one handle. A table adds `useListDisplay(key)` and `useListTable(list, { columns, sortColumns, display })` with columns typed on `ServerTableFeatures` (no `filterFn`, no client sort accessor: only `sortColumns` sort). Render `ListToolbar` (pass `sources` for every unfixed `ref` or `tags` filter; the compiler asks for them), then `ListTable` or `ListBody`. Give `blankSlateAction` the add action; the empty states, count, Load more and ceiling are the parts' own. The header count is `<ListCount count={list.count} noun={def.noun} variant="compact" isLive={false} />`.
6. **A sub-scope is a fixed filter.** An Entity's Identifiers are the Case's list with `fixed: { entityId }`. The route's search for that screen is `UnfixedSearch<typeof def, "entityId">`: drop a hand-typed `entityId` when parsing, so a fixed filter never comes from or goes to the URL. When one route shows two lists (the Dossier's Identifiers and Evidence tabs both own `q` and `sort`), the list params belong to the active tab: parse only that list's (`parseDossierSearch`) and start the other tab at its default view on a tab change.
7. **A tab's count** comes from the first page's `total` of the tab's default view: `useListCount(view, scope, def.queryOf({}, fixed))`, rendered as `<TabCount n={<ListCount … variant="compact" isLive={false} />} />`. It shares the Query key with the tab's own unfiltered view, so it costs no second request.
8. **A URL selection** (`?id=`) is a route param next to the list params. Resolve the row from `list.rows`; only once the first page has landed without it, read it by id with a query whose `enabled` is false without an id (`useSelectedEvidence`). The by-id ServerFn answers null for a row the Case no longer holds (`orpcNullIfNotFound`): clear `?id=` with a short notice. A failed read is `FetchErrorAlert` with Retry, plus Clear selection. Keep `id` out of `loaderDeps`.
9. **Tests.** Component tests drive the real screen against a fake page ServerFn: `vi.fn(memoryListPage(rows, { matches, compare }))` (`src/testing/memory-list.ts`) behind the mocked `*.functions` module, with the route's search held in state the way `usePatchSearch` patches it. Cover search, a filter from the popover, a header sort, Load more, the URL's view on open, blank vs no-match, and, for a selection, a selected row that is not on the first page. Assert what the screen asked the server for (`lastRequest()`), not what it filtered.
10. **Delete the old path in the same change:** the screen's ServerFn and query that read every page, its filter state hook, chip helpers and empty text.

## Gotchas

- **A pre-filtered screen is a link, never a default.** A declaration has no filter defaults, so a screen that should open filtered gets the filter from every link to it: Triage opens on `?status=["pending"]` because the nav link, the Dashboard and Case overview tiles, the palette and every Proposal link carry it (`TRIAGE_PENDING_SEARCH` and `workSearch` in `config/nav.ts`). The route itself shows every status without it, and Clear filters means every status.
- **Choices labels search on the server.** `q` matches the list's declared search fields and the display labels of its `choices` filters, nothing joined: the Identifiers search no longer finds an Entity by name (filter by Entity instead).
- **Pickers search on the server, never the whole list** (#559). A picker reads through a `PickerPort` the domain builds in `queries.ts` (`evidencePickerPort`, `entityPickerPort`): one small page of the declared list (20 rows), newest or most recently updated first while the box is empty, the list's `q` from 3 characters (Evidence reads it as `evidence.pickerPage`, the same list through a slim select: title parts and capture time, about 4 KB a page against 51 KB for the records, #566); and the selected values by id (`evidence.getMany`, `entities.getMany`). `usePickerSource` (`shared/hooks/use-picker-source.ts`) holds the typed text and both reads; `SearchedEvidencePicker` and `SearchedEntityCombobox` (`shared/ui/`) render them, and a `ref` filter's `ListRefSource` comes from the same port (`useEntityRefSource`). The trigger picker reads only while its popover is open, and a `ref` filter's page only once the Filters popover has opened: `ListFiltersButton` tells each ref source through `ListRefSource.onOpenChange`, and the source passes it to `usePickerSource` as `isEnabled` (the chip's title is a by-id read and does not wait).
- **A queue row is a slim projection; the Detail reads the record by id** (#580). The Triage queue, the Dashboard and the Case overview read `proposals.queuePage` (`listProposalQueuePageFn`): the Proposal list's declaration and binding through a select without the patch, so a 50-row page is a few KB instead of 693 KB. A row carries `opCounts` and `evidenceCount`, not the ops; the Detail reads the selected Proposal in full through `proposals.get` (`useSelectedProposal`, always by id, so there is no whole-Case read), and a title with no summary has no Entity name to fall back on. The Detail's Evidence follows the pickers' rule: the Accept picker is `SearchedEvidencePicker`, and the Evidence a Proposal cites is titled by `useRecordsByIdsState`; the preview drawer reads the one record when opened.
- **Linked titles are a by-ids read of the rows on screen.** A row that links Evidence names it through `useRecordsByIds(port, ids)` over the loaded rows' ids (requests of at most `ARRAY_MAX` ids), never a Case-wide map. The Identifiers cell shows only a row's first link, so it reads only those ids.
- **Per-row data is joined into the row, on the server.** A cell never reads a whole list to decorate its row: the Entities table's Connections cell shows `connections` (outgoing and incoming counts) and `soleConnection` from the Entity list's own query, and reads one page of the Connection list (`edgeListView` with `entityId` fixed, the Dossier tab's default view) only while its popover lists them; past that page it says "Showing 50 of M" and links to the Dossier's Connections. Search covers the declared fields only, so a Connection's peer name no longer finds an Entity in the Entities table (open the Dossier's Connections instead).
- **An organization-wide list has no scope param.** Deleted Cases is read in the caller's organization, so its declaration has an empty `scope` and the server's `context` (`{ organizationId }`, never on the wire, in the URL or in a CLI flag): the screen passes `scope: {}`, the view's `scopeKey` is empty, and core authorises (owner or admin) before it calls `listPageEffect` with `{ organizationId }`. Its indexes lead with `organization_id` and are partial over tombstones.
- **A picture is a capped envelope, not a list.** The Graph page cannot draw a page at a time, so it reads `graph.snapshot` once: the server keeps the Case's 150 most connected Entities (Connection count, then most recently updated) and at most 600 Connections between them, and says `isTruncated` when either cap cut something. Only then does the page read `cases.counts` for the notice above the canvas ("Showing 150 of 2,500 entities, the most connected.", or the Connections when only they were cut). The canvas draws what it is given and has no cap of its own. The Dossier ego graph follows the same rule per Entity (#585): `graph.ego` keeps the Entity's `GRAPH_EGO_EDGE_MAX` (60) most recently updated Connections with each peer's label, and the Connections tab says "Showing 60 of 998 connections, the most recently updated." from the tab's own count (the list's first-page `total`, already read for the tab, so no extra request). A drawn Connection the list has not loaded is read by id (`edges.getMany`) before it opens for editing.
- **A Connection is a row with two ends.** The Connection list (`edgeList`) is Case-wide over `edges`; `entityId` matches either end (`or(from_id, to_id)`), so a row carries both ends' labels and the screen orients it (`edgeFromEntity`, `domains/entities/lib/connection-peers.ts`). No single index orders an either-end filter: the binding names it in `selectiveEither`, and the plan gate allows its Sort over the rows the two index lookups found (one Entity's Connections) and checks both indexes are used.
- **A retracted Claim is a view, not a default filter.** The Claim list's `retracted` flag is like Evidence's `hidden`: absent means the live Claims, on means only the retracted, contested and disproved ones (the Dossier's Disproved section is that view with `retracted` fixed). The Questions tab shows open and resolved together, so its count is every Question; `status` narrows it.
- **A board is not a paged list** (#569). Drag and drop needs whole columns, so the Tasks board's open columns are one capped envelope (`tasks.board`: `{ items, isTruncated }` at most `TASK_BOARD_MAX`, read through core's `listCappedEffect` over the Task list's binding in `position` order) that takes the list's own filters and `q`; past the cap the board shows a notice instead of Load more. Its finished columns (Done, Dropped) are the declared list with `status` fixed, each with `ListBody` and Load more, and the toolbar's view narrows all of them. A drag reorders only the cards the board shows (`tasks.reorder` keeps the slots of the others), so a filtered or capped board never needs the whole column. `pagination-coverage.test.ts` lists each capped envelope with its reason.
- **Bulk add is the exception.** Bulk add identifiers matches pasted Entity names in the browser, so it reads the Case's Entities, and only while its dialog is open.
- **Popover bodies and click-opened dialogs are lazy chunks** (#560). `ListFiltersButton` and `ListDisplayButton` (buttons, badge, open state) stay in the route's bundle; their bodies (`parts/filters-popover-body.tsx`, `parts/display-popover-body.tsx`, with the value controls, radio group and checkboxes) load on first open and are warmed on pointer enter or focus of the trigger through `memoizeImport` / `prefetchImport` (`shared/lib/preload-import.ts`; one request shared with `React.lazy`). A body takes plain rows, never the list's generics, so `lazy` needs no cast; its fallback (`PopoverBodyFallback`) only holds the popup's height for the one frame the chunk is in flight. A screen's own click-opened parts follow the same pattern: the Identifiers composer row (`identifier-composer-lazy.tsx`, its add row is the fallback), the bulk-add dialog and the Tasks dialog (mounted on first open, the Tasks one also fetched shortly after the screen mounts). A test that opens a popover waits for its body (`findBy*`). Each route's gzip size is gated by `pnpm check:bundle`.
