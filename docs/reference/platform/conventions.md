# Conventions

Every convention stated in an `AGENTS.md` file or a doc is enforced by a lint rule or gate, labeled `guidance`, or deleted. This table is the one index: rule, where it is stated, and what fails when it is broken. Agents follow what a tool enforces; `guidance` rows are judgment calls checked in review.

**Adding a rule:** add its row here in the same change as the rule (or the prose that states it). Name the enforcer in the `enforced by` cell: a lint rule id, a gate or script (`check:size`), a test file path, a type, or exactly `guidance`. `pnpm check:docs:strict` fails a row with an empty enforcer, a status outside the three below, an `enforced` or `baselined` row that says `guidance`, a named script that no `package.json` defines, or a named test file that does not exist.

**Status:** `enforced` fails the build when broken. `baselined` has an enforcer that tolerates known violations (a shrink-only baseline file or a warn-level rule). `guidance` has no enforcer. A `package.json` dependency list, CSS or a doc is not an enforcer: nothing fails when it changes, so such a rule is `guidance`. One row per rule; `stated in` names the single doc that owns it, and other docs link there. For a rule the code breaks today, the rule cell records the decision (fix and enforce, or delete); the status stays `guidance` until the enforcer exists.

## Adding a lint rule

The [gate freeze](../../contributing/ci-gates.md#gate-freeze) applies: a new rule needs a named regression it would have caught.

Local rules are a single oxlint JS plugin named `watchdog` (`scripts/oxlint-plugin/`, loaded from the `jsPlugins` entry in `oxlint.config.ts`). Reach for a built-in oxlint rule first and configure it in `oxlint.config.ts`; write a plugin rule only when no built-in covers the convention. Land one rule per change so a noisy rule can be reverted alone.

1. **Rule module.** `scripts/oxlint-plugin/rules/<rule-id>.mjs` exports one rule object (`meta` plus `create`). Register it under the same id in `scripts/oxlint-plugin/index.mjs`. Code two rules share goes in `lib/` (`ast.mjs` has the node helpers). Keep every file under 600 lines.
2. **Message.** The report says what to do instead and names where the rule is stated: `<what is wrong>: <the fix, with the helper or path to use> (<conventions row or doc>)`. A message that only says "not allowed" sends the agent guessing.
3. **Config entry.** Enable it in `oxlint.config.ts` as `"watchdog/<rule-id>": "error"`, with an `overrides` block for the trees that are exempt. A rule ships at `error`; a warning is not a gate.
4. **Fixture test.** `scripts/__tests__/oxlint-<rule>.gate.test.ts`, built on `oxlintFixtureFactory` (`scripts/__tests__/helpers/oxlint-fixture.ts`): write violating and passing sources into a throwaway repo that carries the real `oxlint.config.ts` and plugin, lint once in `beforeAll`, and assert the rule id, message and line of each finding with `findingsFor`. Cover every violation shape the rule claims, at least one near miss that must stay legal, and each exempt tree. Add the file to the package's `tsconfig.test.json` coverage (`scripts/tsconfig.test.json` globs `**/*.ts`, so it is automatic there).
5. **Baseline, if the repo already breaks the rule.** Wrap the rule in its own module `rules/no-x.mjs`, where it is exported (`index.mjs` registers the export as is, so a baseline for an unwrapped rule is silently ignored; the layout test fails on one): `export const noX = withBaseline("no-x", { meta, create })` (`lib/baseline.mjs`). Then record today's violations with `node scripts/oxlint-baseline.mjs no-x --init`, which writes `scripts/oxlint-plugin/baselines/no-x.json` (`{ "<file>": <allowed count> }`). The baseline only shrinks: a violation beyond a file's count fails, a count above what the file still has fails as a stale entry, and `node scripts/oxlint-baseline.mjs no-x` lowers counts, drops fixed files and deletes an empty baseline. Fix violations, never raise a count. A normal lint run only checks files that invoke the rule, so a deleted file or a disabled rule leaves its entry unnoticed there; `oxlint-baseline-layout.gate.test.ts` lints every baselined file with the wrapper off and fails an entry whose file is gone or whose count differs from what the rule finds. The script aborts, leaving the baseline untouched, when the scan crashes, fails to parse a file or does not run. Mark the conventions row `baselined`.
6. **Conventions row.** Add the row in this table in the same change: the rule, its scope, where it is stated, `watchdog/<rule-id>` plus the test path as the enforcer, and the status (`enforced`, or `baselined` while a baseline file exists).
