# Jobs, oRPC, and process logging wiring

**What this is:** Cap job enqueue path, oRPC/OpenAPI boundary, where evlog is installed.  
**What this is not:** Cap authoring ([`caps-boundary.md`](caps-boundary.md)), package matrix ([`packages.md`](packages.md)), logging rules ([`../contracts/evlog.md`](../contracts/evlog.md)). Procedure lists are generated: `GET /api/v1/spec.json` and `packages/api`.

## Jobs path

Enqueue: `enqueueCapJobEffect` → pg-boss lane queue (`watchdog.cap-jobs.quick`, `.heavy`, `.act`) → `apps/worker` runs the Cap → Evidence + Proposal → Triage Accept/Reject (one TX). Collect lists jobs via `JobListRecord` (no `logs`); run detail loads the full `JobRecord` via `getJobForCase`. Retry (`jobs.retry`, `retryJobEffect`) starts a new Job from a finished Job's Cap id and input through `startJobEffect` (so credentials and custody checks are identical), stores the original in `jobs.retry_of_job_id` (`JobRecord.retryOfJobId`, null for a first attempt) and leaves the original untouched; a Job that is still queued or running is a `conflict`. A Job of a Playbook run is retried in the same run and step and reopens a finished run (`retry-resume.ts`). One run is read with `jobs.getPlaybookRun` (`GET /cases/{caseId}/playbook-runs/{playbookRunId}`, `playbookRunSchema` in `@watchdog/schemas/jobs`): status, outcome and each recipe step's outcome (`playbookStepViews`), skipped steps with their reasons; `JobRecord` and `JobListRecord` carry only the run's `playbookRunStatus` and `playbookRunOutcome`.

- **One pg-boss per process, as a scoped service.** Enqueue is `enqueueCapJobEffect` with `R = JobQueue`. Web/API compose `jobQueueProducerLayer` (`supervise: false`, starts lazily on the first send); the worker composes `jobQueueWorkerLayer` (`supervise: true`) and the playbook chain reuses that queue. Each Layer releases pg-boss when its scope closes; the worker release is a graceful `boss.stop` bounded by `gracefulStopTimeoutMs()`.
- **Lanes (#478).** The worker runs Jobs in three lanes, each its own pg-boss queue with its own concurrency: `quick` (one-call lookups; queue `watchdog.cap-jobs.quick`), `heavy` (`watchdog.cap-jobs.heavy`: Caps of kind `process`, Caps flagged `slow`, and every system Job such as `system.case_export`) and `act` (`watchdog.cap-jobs.act`: Caps of kind `act`). The lane comes from the Cap's descriptor (`capLane` in `@watchdog/caps/sdk`), so a Cap needs no edit; a Cap may set `lane` to override. `enqueueCapJobEffect` picks the queue (`jobLane`) and `workLanesEffect` registers the handler on all three. Slots per lane and worker process: `WD_WORKER_QUICK_CONCURRENCY` (default 4), `WD_WORKER_HEAVY_CONCURRENCY` (2), `WD_WORKER_ACT_CONCURRENCY` (2) ([`configuration`](configuration.md)). A slow heavy Job holds a heavy slot only, so quick lookups keep running.
- **Act Jobs run at most once.** An act Cap changes something at a provider, so its Job starts from `queued` only: preflight settles it with the `start` event, which has no move from `running`, decided under the row lock. Of two deliveries of one Job (a retry, or a reconcile re-send to another lane queue) exactly one starts it and calls `Cap.run`; a delivery that finds the Job already `running` does nothing (no status change, no failure, no run), decided before input and availability checks so it cannot end as another failure. Nothing takes over a running act Job. A lost attempt (worker died mid-run) is failed by the reconcile stale rule with a fixed message (the action may or may not have taken effect, it was not run again; check the provider, then start it again). Reconcile re-sends only `queued` Jobs, never a `running` one. Other Caps are repeat-safe lookups and are still reclaimed on redelivery.
- **Pool headroom.** A running Job can hold a Postgres connection, and the worker's pool has `POOL_MAX` (10) connections. The worker refuses to boot (`WorkerConfigError`, exit non-zero, naming the three `WD_WORKER_*_CONCURRENCY` settings) when the lane slots sum to more than the pool minus `LANE_POOL_HEADROOM` (2) kept for reconcile, sweeps and the export consumer: with the defaults 4 + 2 + 2 = 8 of 8.
- **Timing derives from Cap `timeoutMs`:** abort, per-job expire, graceful stop, stale-Job reclaim (see [`caps-boundary.md`](caps-boundary.md)).
- **Reconcile.** `reconcileJobsEffect` (`jobs/lifecycle/reconcile.ts`) runs in the worker at boot and every 60 seconds (`JOB_RECONCILE_INTERVAL`), under a transaction-scoped Postgres advisory lock: one worker reconciles, the others skip the tick. It fails `running` Jobs past their Cap's window (`stale`; an unknown Cap is `preflight_failed`), cancels `running` Jobs whose creator lost access to the Case (`access_revoked`, the same check as preflight; the local fiber stops through the cancel poll), re-advances playbook runs with no open Job and re-enqueues `queued` Jobs left without a pg-boss delivery (2-minute `updatedAt` grace; `singletonKey` on send makes repeat enqueue safe). It also rebuilds Cases whose Collect queue projection drifted ([`collect-queue.md`](collect-queue.md)). Each status change is a `settleJobEffect` call, so a repair is one guarded write and one activity entry, and a second tick changes nothing.
- **Export shadow sync:** the worker listens for graph events and calls `scheduleCaseExportEffect` (coalesced in `@watchdog/core`).

**Effect runtime (jobs).** The worker boots `bootWorkerEffect` (`NodeRuntime.runMain`) with stream LISTEN + `cancelPollLoopEffect`. `JobFibers` (FiberMap + the per-attempt stop slots) is provided once. Every abort source (the Cap timer, pg-boss's `job.signal` through `interruptOnQueueSignal`, the cancel poll) offers a `JobStop` (`cause`, `detail`) to the attempt's stop slot, first writer wins, then interrupts the Job fiber; the lifecycle `run` settles the Job once from the slot, so a delivery that outlives its expiry is interrupted, its worker slot freed and the Job marked `failed` with code `cap_timeout` and `Timed out after <expiry>`. `jobs.status` stays the product SoT. pg-boss warnings are persisted (`persistWarnings`, table `pgboss.warning`) and logged at `warn` level. Cap `run` is Effect (`HttpClient` via `httpClientLayer` over the worker's scoped `OutboundClient`, whose pools close after the Job fibers on shutdown; a Job abort aborts its in-flight outbound request); stages keep tagged `E` until `run-job` `catchCause`. Effect 4 sticky interrupt: persist failure via `onExitIf` + map `Fiber.await` in `executeJobOnMap`. The API maps `DomainTag` through `runApp` to `ORPCError`. Deep gotchas: [`packages/core/AGENTS.md`](../../../packages/core/AGENTS.md), [`apps/worker/AGENTS.md`](../../../apps/worker/AGENTS.md). The allowlist for `run*` edges is the `effectRunEdges` list in `oxlint.config.ts`, enforced by `watchdog/no-effect-run-outside-edge`.

**Capability ids** are `<category>.<salient_axis>.<method>`, file path mirroring the id under `packages/caps/src/`. Lexicon and what is enforced: [`caps-lexicon.md`](caps-lexicon.md).

## oRPC

- Router: `packages/api` (`@watchdog/api`): Zod procedures; business logic in `@watchdog/core`; SQL in `@watchdog/db` `repos`.
- **Web UI:** in-process `createRouterClient` through ServerFns (`orpcFromContext`). There is no browser HTTP oRPC and no `/api/rpc` mount. ServerFns are the path for all web reads and writes.
- **OpenAPI (agents/CLI):** `apps/web/src/routes/api/v1.ts` + `v1.$.ts` → `OpenAPIHandler` at `/api/v1`. Spec `GET /api/v1/spec.json`, Scalar `GET /api/v1/`. Security schemes: Bearer, `apiKeyAuth` (`x-api-key`, what `@watchdog/client` and `wd` send), session cookie.
- **Probes:** `GET /api/v1/health` is liveness (always `{ ok: true, service: "watchdog" }`, no dependency) and `GET /api/v1/ready` is readiness, both public. Readiness runs a one-row Postgres read and an object-storage `HeadBucket` in parallel (`checkReadinessEffect`, `@watchdog/core/infra`), each under `READINESS_TIMEOUT_MS` (3 s). It answers 200 with `{ ok: true, database: "ok", storage: "ok" }`, or 503 when either fails. oRPC cannot pick a success status per response, so the 503 is a `SERVICE_UNAVAILABLE` error whose `data` is the same report: `{ ok: false, database: "ok" | "timeout" | "unreachable", storage: "ok" | "timeout" | "unreachable" }`. Reasons are fixed codes; driver messages, hosts and connection strings go to the process log only. Point an orchestrator liveness probe at `health` and its readiness probe at `ready`.
- **Auth context:** `createApiContext` (`@watchdog/auth`) resolves the session cookie or API key into an `ApiActor` with `organizationId` (session `activeOrganizationId`, or the key's `metadata.organizationId`, membership re-checked). `authed` rejects an actor with no organization (403); case-scoped Effects gate on `assertCaseInOrgEffect` ([`../contracts/README.md`](../contracts/README.md#org-isolation)). `ApiContext.log?` is the Start ALS logger when middleware bound one.
- **Organization settings and the external AI handoff:** `organization.getSettings` (any member) and `organization.updateSettings` (owner or admin; core checks `auth.member.role`, a member or non-member is `forbidden`) read and write `organization_settings`. `entities.recordAiHandoff` appends the `handoff` activity entry (actor, Entity, destination; never the text) and is `forbidden` while the organization setting is off; ADR-0005 "As built: #295".
- **External SDK:** `createWatchdogClient({ baseUrl, apiKey })` over `/api/v1`; a blank `apiKey` throws at construction. The contract JSON in `packages/client/src/generated/` is regenerated with `pnpm generate:client`; CI fails on drift. Do not hand-roll `/api/v1` paths. Case Export zip/md are authenticated file routes outside `contract.json` (`wd export` uses raw `fetch` + `x-api-key`).
- oRPC docs: [https://orpc.dev/llms.txt](https://orpc.dev/llms.txt).

## Job log lines (live)

A Job's `jobs.logs` (what `ctx.log` and the stages write) is saved while the Job runs, not only at the end. `createJobLog` (`packages/core/src/jobs/job-log.ts`) keeps the lines in memory with a bound; `withLogFlusher` wraps the Cap or system body in `lifecycle/run.ts` and, every `WD_JOB_LOG_FLUSH_MS` (1000), writes the new lines and appends one `job.logged` activity entry in the same transaction (`flushJobLogEffect`). A chatty Cap is one write per interval, never a row per line. However the body ends (finish, failure, defect, cancel, timeout) the flusher stops and one last save runs before the settle, so a Job cancelled from another process keeps its lines. Bounds: `WD_JOB_LOG_MAX_LINES` (1000) and `WD_JOB_LOG_MAX_KB` (128), each line cut to 1000 characters; past a bound the log ends with one `[log truncated: ...]` line and later lines are dropped, except the run's outcome line (`jobLog.outcome`). The `logged` entry carries the line count, never a line, and is no feed row and no export trigger. It reaches the browser over the one `/api/events` stream, scoped to the caller's organization like every entry; the web app refetches only that Job's detail query (`invalidateAfterJobLog`). A Cap must still never log secrets or Evidence bodies ([`evlog`](../contracts/evlog.md)).

## Process logging (evlog)

Rules live in [`../contracts/evlog.md`](../contracts/evlog.md). Wiring:

- **Sole HTTP emitter:** `apps/web/src/start.ts`, `requestMiddleware: [evlogRequestMiddleware, csrfMiddleware]` (logger outermost; `/api/**` included; health, ready, `spec.json` and Scalar excluded). Do not wrap handlers with `withEvlog` (double emit + private ALS). CSRF is `createCsrfMiddleware({ filter: serverFn })` because the custom `start.ts` disables Start's auto-install; CSRF 403s on `/_serverFn` still emit a warn (`auth.reason: "csrf"`). Keep CSRF after evlog.
- **ServerFns:** `functionMiddleware: [evlogFunctionMiddleware, requireAuth]` in the same file. One wide event per ServerFn; `requireAuth` is global, with no per-function opt-out.
- **oRPC:** `createApiContext` and `orpcFromContext` pass `peekRequestLogger()`; identity is attached once in `createApiContext`.
- **Worker:** `initWatchdogLogger` first in `main()`; Cap Job events come from `executeJobOnMap` as `JobRunOutcome` via `jobWideEventFields` (`outcome` / `stopReason` / `abortReason`, the recorded stop cause / `durationMs`).
- **Drains:** `apps/web/.evlog/logs` and `apps/worker/.evlog/logs` (+ stdout). Hash-chain `.audit/`, `evlog/ai` and Sentry are not built.

## System Jobs and Case export

A system Job (`jobs/system-jobs.ts`, id `system.case_export`) is work the platform runs for a person that is not a Cap: same row, queue, cancel, reclaim, activity entries and `settleJobEffect`, but no catalog entry, input schema, availability check, artifacts, Proposal or cache (`preflightEffect` claims it and answers `kind: "system"`; `capExpireSeconds` and the queue ceilings read `systemJobTimeoutMs`). Its body is `caseExportBody` (`jobs/export-job.ts`), run under `underJobTimer` (`lifecycle/timer.ts`, the Cap timer's own code). The export itself (`export/`): `measureCaseExportEffect` reads Evidence text sizes in SQL (`octet_length`, no bodies) and HEADs stored files `WD_EXPORT_CONCURRENCY` at a time from pages of keys, stopping once the total passes `WD_EXPORT_INLINE_MAX_MB`; `writeCaseExportZipEffect` renders entities and reads Evidence (bodies included) a page of that many rows at a time (`evidenceRepo.listExportPage`, keyset by id), opening files in the same batches and writes them through `ZipWriter` (fflate `Zip`, one chunk at a time, `ZipSink.write` resolves when the reader can take more) into a response body or `multipartSinkEffect` (S3 multipart, 8 MiB parts, aborted when the scope closes before `end`), so memory does not grow with the Case; a file that cannot be opened is skipped and counted, one that fails halfway fails the export. The archive is `exports/{caseId}/{jobId}.zip` (`caseExportObjectKey`; `deleteCaseArtifactsEffect` clears the prefix too). `startCaseExportJobEffect` joins an open export of the Case instead of queueing another (the check and the insert share one transaction under the Case's row lock, `casesRepo.lockById`); `caseExportLinkEffect` answers `pending`, `ended`, `expired` (past the archive's `LastModified` + `WD_EXPORT_LINK_TTL_HOURS`, or the archive is gone; the sweep reads the same rule, `archiveExpiresAtMs`) or `ready` with a signed URL that never outlives the link; `sweepExpiredCaseExportsEffect` (worker, hourly) deletes archives past that same expiry. The user is told by the Job's own `succeeded` activity entry (Recent activity, Jobs queue), not a second channel.

**Provider calls in the Export (#499).** The archive always carries `provider-calls.jsonl` (one envelope per call that backs an exported, non-deleted Evidence item: the fields of the read surfaces' record, `provider-call-view.ts`, plus the `evidenceIds` it backs, `jobProvenance` and a `rawBody` field; URLs are the redacted ones), `ATTRIBUTION.md` (the credit line of each third-party provider whose Cap made one of those calls) and `VERIFY.md` (how to check a body against its SHA-256, and that a match proves only that the stored body is unchanged since receipt, never what the provider sent on the wire). Refused and failed calls of deleted Evidence stay in the install. `served_from_call_id` is followed only inside the exported Case (`toProviderCallRecordsEffect`, over `providerCallsRepo.findIdsInCase`): a foreign id is not exported, and the call reads as served from cache. A raw response (`provider-responses/{callId}.bin`) is included only when every condition of `rawBodyDecision` (`export/provider-body-policy.ts`, the one rule the size pass and the archive share) holds: the body is stored; an owner or admin opted in for this Export; the Cap is not a breach Cap; no `target` contact of the Cap could have named the host, and a fixed contact admits it; and the reviewed verdict in `HOST_REDISTRIBUTION` ([`caps-lexicon`](caps-lexicon.md#providers-and-the-register)) of that host and of every host the call's redirects passed through is `allowed` (`unknown` withholds; a redirect target no fixed contact names is `unknown`, even when the Cap may follow redirects to any public host). The Evidence set is selected once, while the Evidence files are written, and the envelopes, raw bodies and attribution use that same set: Evidence hidden mid-export keeps its envelopes, Evidence added mid-export gets none. `rawBodiesWithheld` counts only calls whose body was stored and then withheld. Breach Evidence (files written by `breach.*` Caps) is written with its credential fields cut to attributes unless `shouldIncludeBreachCredentials` is set (an owner or admin, `requireBreachCredentialOptInEffect`, only while `WD_BREACH_CAPS=full`; the export Job's input carries it and an open export with other options is a `conflict`; the download link of such an archive is `forbidden` to a member or an API key); a file that cannot be parsed is withheld and listed in `VERIFY.md` ([`caps-lexicon`](caps-lexicon.md#breach-credentials-by-mode)). A withheld body keeps its hash and size and carries a fixed `reason` (`RAW_BODY_WITHHELD`); a body that cannot be read back or no longer matches its hash (`readStoredResponseEffect`, the check the download uses) is left out as `unreadable` and the export still finishes. Bodies are written first and the envelopes after (a streaming zip cannot interleave entries), so each envelope says what made it in. **Opt-in:** `GET …/export.zip?rawBodies=1`, or `shouldIncludeRawBodies` in the export Job's `input`. `requireRawBodyOptInEffect` (`export/raw-body-opt-in.ts`) refuses with `ForbiddenError` unless the caller is a signed-in owner or admin: an API key never opts in, whatever its scopes or its owner's role. The streamed download and `startCaseExportJobEffect` both call it. An open export is joined only by a request with the same option (the other gets `ConflictError`, 409), so nobody rides on an export another caller opted into. **Size:** `measureCaseExportEffect` adds the recorded size of the raw bodies the export would include (`measureRawBodyBytesEffect`, from the database, nothing read) to the Evidence bytes before choosing between the stream and a Job; once the Evidence alone is over the limit, no call is read.

## Job start limits

Every path that creates a Job row for a person's request counts the start against the organization and, for an API key, the key, through `takeJobStartEffect(tx, { organizationId, actorKeyId })` (`jobs/start-limits.ts`): `startJobEffect` (Cap runs and, through `retryJobEffect`, retries), `runPlaybookEffect` (the run, not its later steps), the Evidence verbs' `startCapForEvidenceEffect` (a new Job only) and `startCaseExportJobEffect` (a new export only). It is the last step of the creating `transact`, after the Case and Playbook-run row locks, so a refusal rolls the Job and the count back and no two starts can take locks in opposite orders. `jobStartCountersRepo.take` admits a start with one upsert on `job_start_counters` (`scope`, `subject_id`, `window_start`) that raises `count` only while it is below the limit; a concurrent start waits on the row lock and re-reads the count (race tests: `jobs/__tests__/start-limits-two-writers.int.test.ts`). The window start comes from the database clock. The limit is the override in `job_start_limits` (`jobStartLimitsRepo.forStart`) or the instance default (`WD_JOB_START_*`). The worker's re-queue of an existing Job and the chain's step Jobs take nothing. Model, refusal and who may change a limit: [`job-start-limits`](../../how-to/job-start-limits.md).
