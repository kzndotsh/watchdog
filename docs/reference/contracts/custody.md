# Custody contract

**What this is:** Accept confidence tiers and write gates for Graph mutations.  
**What this is not:** Triage UI chrome ([web domains](../web/domains.md)), schema Zod details ([`../platform/types.md`](../platform/types.md)).

## Accept tiers

Platform Accept tiers: **`unverified` / `possible` / `confirmed`**.

- Cap/agent output stays **`unverified`** until human Accept.
- CLI/agent graph writes land at **`unverified`** only; CLI refuses `confidence=confirmed`.
- **Accepting or rejecting a Proposal requires a signed-in session.** `proposals.accept` and `proposals.reject` are built from `sessionAuthed` (`packages/api/src/os.ts`) and answer `FORBIDDEN` to any API key before core runs, whatever its owner's role and scopes (they declare `scope: "session"`); the CLI has no accept or reject verb. Proof: the key path of the isolation matrix (`packages/api/src/__tests__/org-isolation.int.test.ts`).
- **Other administrative actions need a signed-in session too.** Case delete and restore, credential put and delete (vault slots stay per user, with no role check) and organization settings update are `sessionAuthed`, so a key is refused whatever its scopes; the role checks of delete, restore and settings (owner or admin) are unchanged. **A Case's allowed egress** (`allowedEgress` in `cases.update`) is the one field of an otherwise `graph:write` call that needs more: the API layer refuses a key that sends it with `FORBIDDEN`, and core (`updateCaseEffect`, `requireOrganizationManagerEffect`) refuses a member session, so only a signed-in owner or admin changes what a Case may send to outside services. The web form shows the switches read-only to a member. Proof: `packages/api/src/__tests__/session-only.int.test.ts`.
- **`confirmed`** requires human Accept (Triage) or Dossier with evidence gates: never Cap/agent alone. The rule and its message have one home, `packages/policy/src/confirmed-evidence.ts` (`confirmedNeedsEvidence`, `CONFIRMED_REQUIRES_EVIDENCE`; browser subpath `@watchdog/policy/confirmed-evidence`). Callers count the Evidence (attachments, linked job Evidence, an attestation) and pass the total; the message text is never copied (`watchdog/no-reimplemented-custody-message` fails a copy; import `CONFIRMED_REQUIRES_EVIDENCE`).

## Identifier / patch gates

- Invalid Identifier ops **block** Accept (`listInvalidIdentifierOps`).
- Identifier collisions **warn** (Alert + chip); Accept still allowed.
- Custody helpers live in `@watchdog/policy` (`assertPatchGates`, `patchNeedsConfidence`, `childWriteViolation` for the agent/CLI child-write rule shared by API and CLI): pure, DB-free. Browser UI imports `patchNeedsConfidence` from `@watchdog/policy/patch-needs-confidence` only (package root pulls Effect-tagged gates into the client).

Enforced by: the patch schema rejects `confidence` on claim/identifier/edge ops (`packages/schemas/src/patch.ts`), `assertPatchGates` in `@watchdog/policy`, the core write gate (`validateIdentifierWrite`), and CLI custody envelopes (`apps/cli`). Collisions are annotated on `ProposalRecord.identifierCollisions` by core when listing Proposals. The browser-import rule is enforced only by the package exports map; no lint rule.

## Attribution and history

Every Graph row (Entity, Edge, Claim, Identifier, Event, Question) and every Task records who created it and who last changed it, and every change is kept (issue #303).

- **Who.** `created_by` / `updated_by` on the row hold the user id (an API key's write records the key's user; the key's `api-key:...` snapshot and its id are on the history row and the activity entry). `NULL` means no recorded author: a write with no caller (a seed, a script or a cascade). A column, not a sentinel string, so an unknown author can never read as a user.
- **History.** `graph_history` is one append-only table: Case id, row kind and id, op (`create | update | retract | delete`), channel (`dossier | triage_accept | agent_write | system`), actor id, key label and key id (`actor_key_id`: the API key's own id, null for a session or a system write), time, and full-row `before` / `after` snapshots (JSONB, the database's `to_jsonb` of the row; a Claim, Identifier or Edge snapshot also carries its `evidence_ids`). Snapshots, not diffs: any past state reads without replaying; the API derives `changedFields` and returns camelCase keys. A change to the Evidence a Claim, Identifier or Edge cites is an `update` of that row (one row per link statement).
- **Written by the database, not by the application.** AFTER INSERT / UPDATE / DELETE row triggers on the seven Graph tables (`0001_database_logic`) write the history, so no write path can skip it, and a cascade (an Entity delete removing its Claims, a SET NULL on a Task) or a seed or a statement typed in psql is recorded by Postgres itself, in the same transaction as the change (a rollback leaves nothing). An UPDATE that changes only `updated_at` / `updated_by` records nothing; a Claim turning `retracted` is op `retract`.
- **Who and how: four transaction-local settings.** `setHistoryContextEffect(tx, { actorId, actorLabel, actorKeyId, channel })` (`packages/core/src/graph/graph-activity.ts`) runs first in every Graph write transaction and sets `watchdog.actor_id`, `watchdog.actor_label`, `watchdog.actor_key_id`, `watchdog.channel` (`set_config(..., true)`: they end with the transaction). The triggers read them for the history row and fill `created_by` / `updated_by` from the same actor (a statement that sets an author to a different value than the row holds keeps what it set; an UPDATE that leaves `updated_by` as it was takes the actor from the settings, NULL when there are none). The settings are a claim by the writer, as the actor in an activity entry always was; the trigger cannot check them, only that they are there (next item). Core sets them in one place: every Graph write goes through the Graph mutation module (`packages/core/src/graph/mutation/`), whose `runGraphMutation` opens the transaction and sets the context before the body runs, and whose writer appends the activity entry for each write (a patch, Triage Accept or `graph.write`, joins the caller's transaction with `runGraphMutationInTx`; the caller set the context). The gate test `graph-activity-gate.test.ts` fails on a Graph repo write called from anywhere else, except seeds, `test-db` and default-Question seeding: `seedDefaultQuestionsEffect` inserts a new Person Entity's Questions outside the module, by design with no activity entry of their own (the Entity's `created` entry stands for them; the history triggers still record them).
- **The application role must set them.** A BEFORE trigger (`graph_history_context_guard_trg`, `0001_database_logic`, function `graph_require_history_context`) refuses an INSERT, UPDATE or DELETE by `watchdog_app` on the seven Graph tables and the `claim_evidence`, `identifier_evidence` and `edge_evidence` link tables, and a DELETE on `cases` (it cascades into the Graph), when `watchdog.channel` is unset or empty, with SQLSTATE `WD001`; the message names the setting and the HINT names `setHistoryContextEffect`. Core maps it to `InternalError` (a server bug, never caller input). A new write path that forgets the context therefore fails its tests instead of recording a quiet `system` row: the test harness (`withTestTx`) sets no default, and seeds and repository tests that write rows directly say so with `withSystemHistoryContext` / `withSystemTestTx` from `@watchdog/test-db`. The owner role (migrations, seeds run as owner, manual maintenance) is never refused and is recorded as channel `system` with no actor. A cascade of a permitted write is never refused either: a foreign-key action runs as the owner of the referencing table, so the check applies to the statement the application itself issued. The role is matched by name (`current_user = 'watchdog_app'`, the `APP_ROLE` constant; a test keeps the two equal), and a database without that role is unaffected.
- **Never pruned while the Case exists.** No prune job touches it. `UPDATE` is refused for every role; `DELETE` is refused while the Case exists (the Case's own `ON DELETE CASCADE` is the only way rows leave, so a purge takes the history with it); `TRUNCATE` is refused unless the transaction opts in with `SET LOCAL watchdog.allow_history_truncate = 'on'` (`just wipe` and the owner-run `resetTestDb` / `resetE2eDb` do). Every function pins `search_path = pg_catalog, pg_temp` and qualifies every relation with `public.`, so a session cannot shadow `cases` with a temp table, and the functions that write the table are `SECURITY DEFINER`.
- **Roles.** The app, worker and tests connect as `watchdog_app`, which owns nothing; `applyAppRoleGrants` (`packages/db/src/app-role.ts`, run by the migrator after every migration) leaves it `SELECT` on `graph_history` and nothing else (no INSERT, UPDATE, DELETE, TRUNCATE, TRIGGER, REFERENCES), because the trigger functions that write it are `SECURITY DEFINER` and run as the owner. A Case delete still purges it (the cascade runs as the owner). **A single-superuser install is not tamper-resistant:** the role that owns the tables can drop the triggers and rewrite anything. The guard triggers, the pinned `search_path` and the grants are correct for both setups.
- **Not recorded.** Evidence (forensic on its own: hash, source, activity entries) and the link rows themselves; a Case update (a Case is not a Graph row). A future data migration that UPDATEs a Graph table records `system` rows and clears `updated_by` unless it sets it.
- **Read.** `history.list` (oRPC, `GET /cases/{caseId}/history`): one row's history, newest first, organization- and Case-scoped, cursor-paginated (`limit` at most 100, a larger one is rejected), with the live row's creator and last editor. The Dossier shows it per row in a popover.

## Optimistic concurrency

Two people (or a person and an agent) editing the same Graph row must not silently overwrite each other (issue #307).

- **The token.** Each Entity, Edge, Identifier, Claim, Event and Question row carries `version`, an integer that is 1 on insert and +1 on every UPDATE. A monotonic integer, not `updated_at`: two statements in one transaction share `now()`, the Evidence-link touch rewrites `updated_at`, and a timestamp compares by clock, not by count. The BEFORE UPDATE trigger `graph_version_bump` (`0001_database_logic`) owns the increment, so no write path can skip it or set it: a repo, a cascade, a seed and a statement typed in psql all bump it, and so does a change of the Evidence a Claim, Identifier or Edge cites (it touches the parent). `graph_history_row` ignores `version` beside `updated_at` / `updated_by`, so an UPDATE that moves nothing else still records no history, and `changedFields` never lists it. Tasks are case work items, not Graph rows, and stay last-write-wins.
- **Reads return it.** Every Entity, Edge, Identifier, Claim, Event and Question the API returns (lists, gets, and the result of a write) has `version`. A write's result carries the version after the write, so a client can edit again without a re-read.
- **Updates check it.** The update procedures (`entities.update`, `edges.update`, `identifiers.update`, `claims.update`, `events.update`, `questions.update`) require `expectedVersion`. The repo adds `AND version = $n` to the UPDATE's WHERE, so of two writers that read the same version exactly one matches a row; there is no read-then-write window. An edit that also replaces the Evidence links (Claim, Identifier, Edge) takes the row's lock first with `SELECT … WHERE id AND version FOR UPDATE`, because replacing the links bumps the version (and would otherwise change the history `before` snapshot of the link change): the check is the same atomic compare, and the lock holds to the end of the transaction. `claims.retract`, `questions.resolve` and `questions.reopen` are already conditional on the row's state (`retracted = false`, `status`) and take no version; they still bump it.
- **The conflict.** A miss where the row still exists fails with `StaleVersionError` (`code: "stale_version"`, HTTP 409, transport `CONFLICT`), message `<Entity> changed since you opened it`, and `data: { code: "stale_version", entity, id, currentVersion }`. Nothing was written. A row that is gone is `not_found` as before. The code is stable; the CLI prints it as `error.code` (see [`agent-cli`](../../how-to/agent-cli.md#notes-by-verb)).
- **Patches (`graph.write`, Triage Accept).** A patch op may carry `expectedVersion`. When it does and the row has moved on, the whole patch fails with `stale_version` and rolls back (nothing is applied, no `graph_writes` row); an op without it overwrites the row as it stands, as before. Only an op that changes an existing row reads it: entity `update`, and an `upsert` that lands on an existing entity, identifier or edge (claim, event and question ops only create). Triage Accept applies the Proposal's patch the same way: Caps have no database access and cannot know a row's version, so a Cap's Proposal carries none and Accept stays unconditional (the human reviewed the Proposal, and Accept lands `unverified`); an agent that proposes with `expectedVersion` gets it enforced at Accept.
- **Web.** Every edit surface sends the version it loaded (an editor sends the version at the moment it opened, not the list's latest). On `stale_version` a toast says the row "changed since you opened it" with a Reload action that refetches the Entity's caches (`invalidateAfterEntityChanged`) and closes the editor.

Tests: `packages/core/src/graph/mutation/__tests__/conformance.int.test.ts` (every Graph table: two writers, stale and missing rows, Evidence edits), `packages/core/src/graph/__tests__/optimistic-concurrency.int.test.ts` (patch ops), `packages/api/src/procedures/__tests__/stale-version.int.test.ts`, `packages/api/src/__tests__/error-map.test.ts`.

## Database invariants

Postgres refuses these on its own, so a bug in application code cannot store them (tests: `packages/db/src/__tests__/vocabulary-checks.int.test.ts`, `same-case-integrity.int.test.ts`; `0000_baseline` and `0001_database_logic`):

- **Vocabulary.** Every status, kind, confidence, predicate and channel column has a `CHECK` generated from `@watchdog/schemas` (table in [`types`](../platform/types.md#vocabulary-constraints-in-postgres)). A value outside the vocabulary is a `23514` check violation.
- **Same Case.** Claims, Identifiers, Events, Questions and Edges carry `case_id`, and a composite foreign key `(entity_id, case_id)` into `entities (id, case_id)` (an Edge has one per end, `from_id` and `to_id`) means a row cannot name an Entity of another Case. Every Evidence link table (`claim_evidence`, `identifier_evidence`, `edge_evidence`, `proposal_evidence`, `job_evidence`) carries `case_id` with two composite keys, `(parent_id, case_id)` and `(evidence_id, case_id)`, so the parent and the Evidence must both be in the link's Case. `evidence.entity_id` and `tasks.entity_id` are held to the same Case the same way. A cross-Case row is a `23503` foreign key violation.
- **Evidence ids on Proposals and Jobs** are rows in `proposal_evidence` and `job_evidence` (position-ordered, real foreign keys), not JSON arrays. The API still returns `evidenceIds` arrays, read from the link tables in the same statement.
- **Deleting.** Claim, Identifier and Edge links go with either end (`on delete cascade`). Proposal and Job links go with their Proposal or Job but **restrict** the Evidence end: Evidence is forensic, so a hard delete of Evidence that a Proposal or Job still cites is refused (`23001`). The application never hard-deletes Evidence (it sets `deleted_at`). A Case delete still removes everything, Evidence included: a `BEFORE DELETE` trigger on `cases` (`evidence_links_before_case_delete`) removes the Case's Proposal and Job links first, because Postgres checks a restrict when the cascaded Evidence delete finishes, before the cascade reaches the Job. Deleting an Entity clears `evidence.entity_id` and `tasks.entity_id` (`ON DELETE SET NULL ("entity_id")`: the Case id stays) and removes the rows that hang off it.
- **By design still JSON, without a foreign key:** the Evidence ids inside `proposals.patch` and `graph_writes.patch` (`PatchOp.evidenceIds`). A patch is the record of what was proposed or written; Accept and the agent write path check those ids against the Case before the Graph rows and their links are created.

Not enforced by Postgres (still application rules): `confirmed` needs Evidence (above), the Entity-kind pairs an Edge predicate allows, the `(kind, verb)` pairing of the activity log, and the Case of `proposals.job_id`, `jobs.playbook_run_id`, `jobs.retry_of_job_id` and `finding_suppressions.proposal_id` (soft or single-column references).

## Evidence uploads

A file's hash on Evidence is the server's own, computed from the stored bytes; the hash the browser or CLI sends is a claim the server checks, never a value it records (#305).

- **Presign records what is pending.** `evidence.presign` stores a row in `evidence_uploads` per object key (`{caseId}/{sha256}/{name}`): the declared hash, type and size, who asked and when. The key is content-addressed, so a repeat presign of the same file refreshes the one row (the window restarts). The row is not Graph and not audit; it goes with the Case.
- **The store enforces the size.** The presigned PUT signs `Content-Length` with the declared size, so the object store refuses a body of any other length before it is stored. The declared size is capped by `MAX_UPLOAD_BYTES` (100 MiB). That is a separate limit from `REQUEST_BODY_MAX_BYTES` (2 MiB), which bounds every API and server-function body: the file never passes through the web app, only its metadata does, so the two cannot disagree.
- **Confirmation verifies the object.** `evidence.confirmFile` is refused unless the key was presigned in this Case with the same hash, type and size. It then reads the object: size from `HEAD` first (a different size is refused before any byte is read), then one streamed read bounded by the declared size that computes the SHA-256 and keeps only the first kilobyte. A hash that differs from the declared one, a stored `Content-Type` that differs, or leading bytes that name a different format than the declared type (PNG, JPEG, GIF, WebP, PDF, ZIP and its office formats, gzip; other content is not judged) is an `invalid` refusal and nothing is recorded. A missing object is `invalid`; an unreachable store is `internal`. The Evidence row takes the hash the server computed, and the upload row is marked confirmed in the same transaction as the Evidence and its `captured` activity entry.
- **Raw bytes are kept.** The stored object is never rewritten or transcoded; a confirmed object stays under its key for the life of the Case.
- **Orphan sweep.** The worker deletes the object of every upload still unconfirmed 24 hours after its presign, at boot and then hourly (`sweepAbandonedUploadsEffect`, at most 500 a run, oldest first). Rows are locked (`FOR UPDATE SKIP LOCKED`) while their objects are deleted, in one transaction: a confirmation that races the sweep either takes the row first (the sweep skips it) or is refused as expired once the row is gone, so Evidence never points at a deleted object. A key that backs any Evidence row (hidden or not) is never deleted, even when the same file was presigned again and left unconfirmed. A failed store delete rolls back and the next run retries; a second run finds nothing. A refused confirmation leaves its object for the sweep.

Tests: `packages/core/src/evidence/__tests__/evidence-upload.int.test.ts` (confirm, refusals, the live store), `upload-sweep.int.test.ts`, `packages/core/src/infra/__tests__/blob-verify.test.ts`.

## Deletion and retention

Deleting a Case is a tombstone, not an erase (issue #304). Content is erased only by a purge, and a minimal permanent record survives it.

- **Tombstone.** `cases.deleted_at`, `deleted_by` (the user id; an API key's user) and `purge_after` (the end of the restore window, fixed at delete time from the deleting process's `WD_CASE_RETENTION_DAYS`; a later change of the setting does not move it). Nothing else changes: the Graph, its history, Evidence, the activity log and `graph_writes` stay exactly as they were, so a restore brings back everything. The same transaction cancels the Case's queued and running Jobs and its running playbook runs (the existing cancel path: status `cancelled`, a `cancelled` activity entry per Job, and the worker's cancel poll aborts a running one), writes the `deleted` record and a Case-level `deleted` activity entry, and drops the Case's Export shadow folder. A cancelled Job is not resumed by a restore. **The slug is freed at once**: `cases_organization_id_slug_uidx` is unique over visible Cases only (`WHERE deleted_at IS NULL`), so a new Case can take it. A restore into a taken slug de-conflicts with the first free `slug-2`, `slug-3`, ...; the `restore` answer carries `previousSlug` and the restore toast says so (the `restored` record names the slug it came back under).
- **One visibility predicate.** `visibleCase` (`packages/db/src/repos/_visible-case.ts`, `deleted_at IS NULL`) is taken by every read of `cases` and every join that decides whether a caller may see Case data: the Case list, `getById`, `getBySlug`, `lockById`, search, `listVisibleCaseIdsEffect`, `assertCaseInOrgEffect` (so every Case-scoped procedure, Collect, Triage and Dossier included), the Active Case rule, the Recent activity feed and the live replay (`orgCaseFilter`), the Entity-with-Case read behind Export, the worker's Case reads (export, Cap availability, the Cap Job's pre-flight: a Job on a deleted Case is cancelled instead of run, `case_deleted`) and the export consumer's re-scan. A deleted Case is invisible to every procedure, like another organization's Case: the matrix test attacks the router with a deleted Case and expects `not_found` from each (`packages/api/src/__tests__/org-isolation.int.test.ts`). The only readers that look past it are named for it: `*IncludingDeleted` reads a Case in any state (`getByIdIncludingDeleted`, `listIdsIncludingDeleted`), `*Deleted*` reads or changes tombstones only and takes the twin predicate `tombstonedCase` (`deletedCaseListRepo`, `getDeletedBySlug`, `listDeletedPurgeDueIds`, `lockDeletedForPurge`, `restoreDeleted`, `markDeletedPurgeStarted`, `recordDeletedPurgeError`, `purgeDeleted`).
- **Background work stops when its author loses access (#371).** A Job's pre-flight re-checks its creator before it runs: still a member of the Case's organization, not banned, and, when an API key started it (`jobs.actor_key_id`, no foreign key so a deleted key shows as missing), the key still exists, belongs to the creator, is enabled and has not expired. A failed check cancels the Job with a reason in `error` (`access_revoked`); a Playbook step carries the run's key id to every later step, so each is checked again, and a cancelled step ends the run. Code: `packages/core/src/jobs/job-access.ts`, `stages/preflight.ts`; test: `packages/core/src/jobs/__tests__/job-access.int.test.ts`.
- **Who may.** Delete, restore and purge need an owner or admin of the organization (`requireOrganizationManagerEffect`, the check team management and organization settings use; a member could delete a Case before #304 and no longer can). **Delete, restore and purge are refused for any API key** (`sessionAuthed` in `packages/api/src/os.ts`), whatever its owner's role or scopes (key scopes: [`agent-ingress`](agent-ingress.md#key-scopes)); the CLI has no delete or restore verb. A foreign, missing or already deleted Case is `not_found` for delete; a member gets `forbidden` for restore, purge and the list. The deleted-Case URL answers `not_found` to a member, so it never says that a deleted Case exists. **Check order** (one rule for delete, restore and purge): the role first, then the Case. A caller who may not manage Cases gets `forbidden` whatever id they send, so the answer never reveals whether a Case exists; a manager gets `not_found` for a foreign or missing Case.
- **Restore window.** `WD_CASE_RETENTION_DAYS` (default 30, read when a Case is deleted and stored on the row as `purge_after`; restore, the scheduled purge and the "days left" all use the row's date, [`configuration`](../platform/configuration.md)). Restore is refused (`conflict`) once `purge_after` has passed (the UI disables Restore with the reason), and once a purge has begun (the files may be partly erased); the Case can then only be purged.
- **Purge.** The worker purges every tombstone past the window, plus any purge that began and did not finish, at boot and then hourly (`purgeExpiredCasesEffect`, at most 20 Cases a run). Owners and admins can purge now from Deleted Cases (`cases.purge`, session only). Per Case, in three steps that are each safe to repeat: (1) lock the tombstone with `FOR UPDATE SKIP LOCKED` and, the first time, write the `purge_started` record and set `purge_started_at` (a restore is refused from here); (2) delete every object under `{caseId}/` (a failed delete, including S3's per-key `Errors` answer, is recorded on the Case as `purge_error` with a `purge_failed` record when the message is new (the same failure on an hourly retry writes nothing), shown in Deleted Cases, and retried by the next run: the Case stays deleted and listed, never invisible and never half-purged without a trace); (3) in one transaction set the `system` history context the application role needs for a Case delete (#352), write the `purged` record with row counts first, and delete the Case, whose foreign keys cascade through the Graph, `graph_history`, Evidence, Jobs and the activity log. A second sweep of the objects follows the commit. **No owner login is needed**: a cascade runs as the owner of the table it deletes from, so `watchdog_app` (the worker's role) removes `graph_writes` and `graph_history` rows with the Case although it may not delete them itself. Two purges at once are safe (the Case delete and the `purged` record happen once, in the one that holds the row lock; the other moves on, though both may list and delete the same objects, which is idempotent) and a second run finds nothing. **Purge now never reports success unless the Case is gone**: when its claim is skipped because another transaction holds the Case, it waits for that transaction (`FOR SHARE`) and re-reads; a Case that was restored meanwhile, or is still deleted, is a `conflict`. A failing Case is tried after the fresh ones, so a few failures cannot starve later Cases. The second object sweep after the commit is best effort: if it fails, a file a straggling Job wrote during the purge can remain, and it is logged (`case.purge.sweep`).
- **The deletion record.** `case_deletion_records` is append-only and has no foreign key to `cases`, so it outlives the purge: one row per `deleted`, `restored`, `purge_started`, `purge_failed` and `purged` event with the Case id, organization id, the Case's name and slug at that moment, who did it (`actor_id`, `actor_label`: an API key's `api-key:...` snapshot, or `system` for the scheduled purge) and when (plus an `xid` column, the writing transaction's id, that the lifecycle guard below compares); a `purged` row also carries `counts` of what went (entities, edges, claims, identifiers, events, questions, tasks, evidence, proposals, jobs, playbook runs, graph writes, graph history, activity entries, cached Cap results, finding suppressions, provider calls, call outcomes, Evidence-to-call links, and the raw provider-response bodies in the object store as `providerRawBodies`). It is in `AUDIT_TABLES`: `watchdog_app` may insert and read it, never update, delete or truncate it. It holds no content. The spec's idea of a minimal stub of each agent graph write is not kept: the counts record that they existed and the record is the trace.
- **Provider calls (#495).** What a Job asked a provider and what came back is stored, so an investigator can show what a provider returned, when, and prove the stored body is unchanged since receipt. `provider_calls` (the request side: redacted URL, method, request-body hash, start time) is inserted before the call is sent, so a worker crash still leaves it. `provider_call_outcomes` (status, allowlisted headers, timing, body state and hash) is inserted when the call ends, and on a successful run before the Evidence lands (a failure to save fails the Job); a failed or cancelled run saves best effort, and `jobs.provenance_state` `incomplete` marks a gap. A run flags the Job `incomplete` before it saves anything and writes `complete` back only after every outcome and body is stored (and only over a flag it set itself: both writes are conditional on the current state, and a stop that interrupts the first write still flags the Job), so a timeout, failure or stop anywhere leaves `incomplete`, never a false `complete`; a failed write back is a false gap, the safe direction. A stop is bounded by one budget for the flag, the save and the follow-up write. `evidence_provider_calls` links Evidence to the calls of the run that produced it, or for a cache hit the run the cache came from (`jobs.cache_source_job_id`). All three are in `AUDIT_TABLES` (the application role inserts and reads; update, delete and truncate are refused by privilege), carry the Case id in composite foreign keys so a cross-Case link is refused, and cascade with the Case. The `cases` BEFORE DELETE trigger that clears the Evidence link tables is `SECURITY DEFINER` so a Case delete can also clear `evidence_provider_calls`, which the application role cannot delete itself. Raw bodies sit in the object store under the Case's prefix (`{caseId}/{sha256}/provider-response`), up to a keep limit; over it, and always for `breach.*` Caps and model calls, only the hash and size are kept. A purge erases rows and objects with the Case and counts them in the `purged` record. Stored bodies are what the Cap received (the transport has decoded any Content-Encoding), so the hash proves the stored body, not the wire bytes. Detail: [`caps-boundary`](../platform/caps-boundary.md#outbound-http).
- **Reading provider calls (#498).** `evidence.listProviderCalls` and `jobs.listProviderCalls` (`cases:read`) list the calls behind an Evidence item and the calls of a Job: method, redacted URL, transport, outcome, status, timing, request and response body state with size and hash, the provider's content type, and the Cap and version of the Job that made the call. Both reads are organization- and Case-scoped by `assertCaseInOrgEffect`, so another organization's member, or an id from another Case, gets `not_found`. Both lists are bounded (`calls` with `isTruncated`, `cacheHits` with `areCacheHitsTruncated`). A record with a gap says `provenance: "incomplete"` (a Job marked `incomplete`, or Evidence a Job marked `incomplete` landed; read from the Jobs themselves, so a Job whose calls fall past the cut still counts). A Job produced an Evidence item, as opposed to only reading it as a Process Cap's source, when the item's object is one of the Job's output artifacts; only producing Jobs count towards a cache hit or a gap: an empty list is then a gap, never "no calls". The two soft references (`served_from_call_id`, `jobs.cache_source_job_id`) may name a row of another Case or organization, because the feed caches are shared by the process. They are followed only inside the caller's Case: the lookup is `case_id`-scoped in SQL, so an original outside it is `null` and the call still says it was served from cache, with nothing about the other row read or returned. `GET /api/v1/cases/{caseId}/provider-calls/{callId}/response` (`cases:read`) serves a stored raw response (`body_state = stored`) only as an attachment: `Content-Type: application/octet-stream`, `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, never inline. The provider's own content type stays in the record. The bytes are read against the recorded size and checked against the recorded SHA-256, and a body that no longer matches is a 500, never served. A call of another Case or organization, a hashed or partial body and an unknown id are the same 404.
- **The database enforces the lifecycle** (`cases_lifecycle_guard`, `0001_database_logic`, SQLSTATE `WD002`). For the application role `watchdog_app`, a BEFORE trigger on `cases` refuses: a DELETE of a Case that is not tombstoned, or without a `purged` record of the same transaction; a change of `deleted_at`, `deleted_by`, `purge_after`, `purge_started_at` or `purge_error` without a matching record of the same transaction (`deleted`, `restored`, `purge_started`, `purge_failed`, or any record for another change of those columns); and a restore once `purge_started_at` is set, or taking a begun purge back. "Same transaction" is the record's `xid` (default `pg_current_xact_id()`) equal to the current transaction, so the record is written first, by `recordDeletionEventEffect` (`packages/core/src/cases/deletion-event.ts`, the one writer), and an old record proves nothing. The function pins `search_path = pg_catalog, pg_temp` and qualifies every name, like the other functions of `0001_database_logic`. **Owner maintenance** is the documented way around it: the table owner (`DATABASE_URL_MIGRATE`: migrations, `just wipe`, the owner-run test reset, manual repair) is never refused and leaves no record; it is not tamper-resistant against the owner, who can drop the trigger. The Better Auth organization delete runs in the app (role `watchdog_app`) through `deleteOrganizationCasesEffect`, which tombstones and purges each Case with its records, so it needs no owner path. Proof: `packages/db/src/__tests__/case-lifecycle-guard.int.test.ts` (each refusal and the normal flows as `watchdog_app`, the owner exemption) and the organization-delete test in `tombstone.int.test.ts`.
- **Logged.** A delete and a restore each append one Case-level activity entry (`kind case`, action `deleted` / `restored`, the Case as subject) in the same transaction, through `recordDeletionEventEffect`, so other open sessions refresh; the cancelled Jobs append their own `cancelled` entries. A purge appends nothing (it would cascade the entry away), and the permanent deletion record is its trace. A client that is open on a deleted Case finds out at its next request (`not_found`).
- **Backups.** A backup taken before a purge still holds the Case, and one taken during the window holds it too. Erasing a Case for good also means expiring those backups ([`backup-restore`](../../how-to/backup-restore.md#deleted-cases-and-backups)).

## Breach credentials

What a breach Cap keeps of a recovered password or hash, and what an Export carries, depends on `WD_BREACH_CAPS` (`off`, `safe`, `full`): [`caps-lexicon`](../platform/caps-lexicon.md#breach-credentials-by-mode) has the table, the reuse fingerprint and the key derivation. In short: in `safe` mode Evidence never holds a plaintext password or password hash (present, kind, length and a keyed fingerprint only); in `full` mode Evidence keeps them, and a Case Export cuts them to those attributes unless an owner or admin includes breach credentials for that Export (`?breachCredentials=1`, never an API key, never in `safe` mode). Raw provider responses of breach Caps are fingerprint-only in every mode and never exported. A Claim never quotes a credential.

**Watchdog never uses a retrieved credential to log in to anything, and no feature may.** Using a recovered password or hash to access an account is unauthorised access under the UK Computer Misuse Act 1990 s.1 and the US Computer Fraud and Abuse Act, whatever the mode and whoever asks. Credentials are evidence that a record exists in a dump; nothing in Watchdog tests, replays or submits them.

Follow-ups: #539 (reveal with an audit log) and #540 (a retention limit).

## Breach caveat

Treat a breach hit as evidence that a record exists in a dump, not as proof the person controls the account. Adversarial-test every identity link before proposing it (guidance; nothing enforces it). Cap D5: [`../platform/caps-lexicon.md`](../platform/caps-lexicon.md).
