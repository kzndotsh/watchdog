# ADR-0007: One list standard: a declaration per list and one canonical query

**Status:** accepted (2026-10-25) · spec [#547](https://github.com/kzndotsh/watchdog/issues/547), first slice [#548](https://github.com/kzndotsh/watchdog/issues/548) (the declaration) **What this is:** how every list (Evidence, Identifiers, then Entities, Triage and the rest) states its filters, sorts and search once, and how the API, the SQL, the route URL, the Query cache, the CLI and the toolbar derive from that one statement. **What this is not:** the list UI's look (spec #547), the SQL bindings and the conformance test (#549), or a rule for small bounded lists (settings, Vault, Library, credentials), which stay client-side under a server-enforced maximum.

## Context

Every list is paged by keyset on the server ([types: Pagination](../reference/platform/types.md#pagination)), but no list takes a sort, a text search or returns a total. The web reads every page anyway (`listAllPages`) and sorts, filters and searches in the browser. That is correct for small Cases and quietly wrong once a screen holds a window instead of everything: browser-side search only sees the loaded rows. Each screen also does it its own way: five kinds of search box, three ways to reset filters, five ways to show counts, two hand-made "Show more" buttons and per-screen filter state.

Four places must agree on what "the same view" is: the URL, the Query cache key, the cursor and the row selection. Today nothing makes them agree. Five surfaces must give one meaning to a list request: the oRPC input and output, the SQL, the route's `validateSearch`, the CLI flags and the toolbar. `@watchdog/schemas` is a Zod-only leaf (no db, no web), `core` has no SQL, and the CLI's contract is `{ cursor, limit }` in and `{ items, nextCursor }` out.

## Decision

1. **One declaration per list, in `@watchdog/schemas`, holding data only.** `defineList({ name, noun, scope, filters, exclusive?, sorts, defaultSort, search? })` (`packages/schemas/src/lists/define-list.ts`) declares the filters, the sort options, the searchable fields and their labels. Each list lives in its domain subpath (`evidenceList` in `@watchdog/schemas/evidence`, `identifierList` in `@watchdog/schemas/graph`); every declared list is in `LIST_DEFS` (`@watchdog/schemas/testing`). Labels live in the declaration, so the CLI help, OpenAPI and the toolbar share them, and they reuse the vocabulary labels in `display-labels.ts`.
2. **Four closed filter kinds** (`packages/schemas/src/lists/filter-kinds.ts`): `flag` (true-only: on or absent, never `false`), `choices` (any of a closed vocabulary), `ref` (a row of another list, by id) and `tags` (any of an open vocabulary). Each kind carries its label, a bounded wire schema, a URL schema and a CLI parser, and has one canonical form. Every interpreter (wire, URL, CLI, SQL predicate, toolbar control) is one exhaustive `switch (filter.kind)`, so a new list needs no code in any of them and a fifth kind fails typecheck everywhere until it is handled. There are no operators, no OR groups and **no filter defaults**: absent means everything, and a screen that opens pre-filtered links with the filter in its URL (the Triage nav link carries `?status=pending`), so Clear and chip removal always mean what they say.
3. **One canonical query.** `def.queryOf(search, fixed?)` normalises a view (drops empty values, orders arrays, trims `q`, fills the default sort, resolves an `exclusive` pair) and `def.keyOf(query)` serialises it. That one string is the Query key tail, the cursor fingerprint input, the selection key and, through `def.toSearch`, the URL. Only `defineList` canonicalises, so the four cannot disagree. `withFilter`, `isFiltered` and `cleared` are the only ways a screen changes or reads a view.
4. **Types reach both ends.** `def.input` is `ZodType<ListInput<D>, ListWireInput<D>>`, so the oRPC client argument is exact: an unknown key, a bad enum value, `false` on a flag and an undeclared sort are compile errors. `def.searchWith(extra)` outputs exactly `ListSearch<D> & extra`, so `Route.useSearch()` needs no cast. The declaration itself rejects a reserved filter name (`q`, `sort`, `cursor`, `limit`), a filter named like a scope key, an undeclared `defaultSort`, a direction listed twice and an `exclusive` pair that is not two different declared filters. Generic code (registries, the conformance harness, `useList`) holds the erased `AnyListDef` and reaches the typed API through `opsOf(def)`: a cast at that one erased boundary, and in `defineList` where the runtime builder meets its typed view, nowhere else.
5. **Sub-scope is a fixed filter.** "Identifiers of this Entity" is the Case's Identifiers list with `entityId` fixed. A fixed filter is part of the query and the key, never in the URL (the types forbid it in the search and in the patch), never a chip, never cleared and not counted by `isFiltered`, so a Dossier tab still says "No evidence yet". The per-Entity list procedures merge into the Case-wide ones.
6. **Search is `q`, at least 3 characters, in the list's own sort order.** A trimmed `q` of 1 or 2 characters is a 400 on the wire and a usage error in the CLI; only the URL drops it quietly. It is backed by `pg_trgm` indexes on the list's own columns plus the display labels of its `choices` filters; the command palette keeps its wider search.
7. **The output is `ListPage<T> = Page<T> & { total }`.** `total` is `{ count, isCapped }` on the first page only (capped at `LIST_TOTAL_CAP`, 1,000, shown as "1,000+") and null after, so CLI callers of `Page<T>` keep compiling. Paging stays keyset; the cursor carries the sort and a fingerprint of the query, and reusing it for another view is a 400 with `cursor_stale`. One view loads at most `LIST_MAX_PAGES` (10) pages.
8. **SQL binds to the declaration in `@watchdog/db`, typed against it** (#549): one predicate per filter receiving that filter's exact value type, each sort bound to a NOT NULL column of the list's table whose type matches the declared key type (or an explicit sentinel), search columns of the same table. A binding that leaves something out or binds the wrong column type does not compile.

## Consequences

- A new list is one declaration and one db binding; the API input, the URL schema, the CLI flags and the toolbar come from them, and the compiler names what was forgotten.
- Search, sort and filters give correct answers over every row, and a view is shareable and bookmarkable through its URL.
- The wire changes for the pilot lists: Evidence's `hiddenOnly` / `unprocessedOnly` / `unattachedOnly` become true-only flags `hidden` / `unprocessed` / `unattached`, and `hidden=false` from an external caller becomes a 400. There are no live installs to migrate.
- List search is narrower than the palette's: no joined fields, no Evidence bodies. In exchange `q` always uses an index.
- `@watchdog/schemas` owns labels and pure functions for every list, which makes it larger, but it stays Zod-only.

## Considered

- **Column metadata drives the controls** (a table column declares that it filters or sorts, and the toolbar reads the columns). Rejected: queue screens have no columns, a filter belongs to the list rather than to one rendering of it, and the CLI and the API would have to reach into web table definitions.
- **The declaration carries its own SQL** (predicates and sort columns inside the `defineList` call). Rejected: `@watchdog/schemas` cannot import drizzle or the db package, and raw SQL is allowed only in `db/_*.ts` and the schema files. A typed binding in `@watchdog/db`, checked against the declaration, gives the same guarantee (a missing filter or a wrong column type does not compile) without breaking the boundary.
- **Per-list hooks** (`useEvidenceList`, `useIdentifierList`, each with its own filter state, URL parsing and query keys). Rejected: that is today's state of five search boxes and three reset behaviours, and nothing would make the URL, the cache key, the cursor and the selection agree. One `useList(view, { scope, fixed?, search, onSearchChange })` driven by the declaration gives every list the same behaviour.
- **The cursor carries the whole query.** Rejected: every request keeps its flat params; the cursor carries only a fingerprint that detects reuse for another view.
- **Filter defaults** (Triage pending-only by default). Rejected: they make Clear and chip removal lie; a link carries the pre-filter instead.
- **One facet button per filter.** Rejected in favour of one Filters popover with an active-count badge.

## Reopen when

- a list needs an operator or an OR group that no combination of the four kinds expresses, or
- the `q` budget (p95 at most 50 ms at audit scale for the worst 3-character needle) fails in the conformance run, or a searched table passes 1,000,000 rows: switch that table to Case-scoped `btree_gin` trigram indexes, or
- a list needs to sort by a joined column.
