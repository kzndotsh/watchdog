# Worker app (`@watchdog/worker`)

> Scope: `apps/worker` (inherits root [AGENTS.md](../../AGENTS.md) unless noted)

Thin Cap Job runner: pg-boss `work` → `executeJobOnMap`, a cancel poll, the activity log consumer → `claimCaseExportEffect`, and core's maintenance list. Logic stays in `@watchdog/core`; the worker has no `@watchdog/db` dependency, so it cannot run SQL.

## Commands

| Task                    | Command                                    |
| ----------------------- | ------------------------------------------ |
| Dev                     | `pnpm dev:worker`                          |
| Typecheck (src + tests) | `pnpm --filter @watchdog/worker typecheck` |
| Unit tests              | `pnpm test:unit`                           |

## Gotchas

- The container image runs the bundle `pnpm --filter @watchdog/worker build` writes (`dist/worker.mjs`, esbuild, every dependency inlined), not tsx. The `worker` target skips migrations by default (`WD_SKIP_MIGRATIONS=1`; the web container migrates). Boot code must not read files beside the source tree: `import.meta.dirname` is `/app` in the image. See [`self-host`](../../docs/how-to/self-host.md).
- The handler wraps each delivery in core's `interruptOnQueueSignal` (pg-boss `job.signal` → core's `stop` with a cause), so an expired delivery interrupts its Job (failed, code `cap_timeout`, `Timed out after <expiry>`) and frees the single worker slot. pg-boss warnings are persisted and logged at `warn` level; `QueuedJob` carries `signal` and `expireInSeconds`.
- Job execution, cancel/abort, `JobFibers`, and one-boss-per-process: single home is [`effect/references/jobs.md`](../../.agents/skills/effect/references/jobs.md). The queue is the `JobQueue` + `JobQueueWorker` services from `jobQueueWorkerLayer` (never construct a boss here); the playbook chain is core's `advancePlaybookRunEffect`.
- Lanes (#478): `registerCapJobHandlerEffect` calls core's `workLanesEffect`, one handler per lane (`quick`, `heavy`, `act`; each a pg-boss queue) with `localConcurrency` from `WD_WORKER_{QUICK,HEAVY,ACT}_CONCURRENCY`, so a slow heavy Job never delays a quick lookup. The lane of a Job is its Cap's (`capLane`) or heavy for a system Job; the worker never picks one. An act Job starts from `queued` only (`start`, under the row lock): a second delivery finds it running and does nothing, and reconcile fails a lost one with the act message (at most once). Boot refuses (`WorkerConfigError`) when the lane slots exceed the pool minus 2 (`laneSlotsFit`). Detail: [`jobs-orpc`](../../docs/reference/platform/jobs-orpc.md).
- Cap `timeoutMs` (from Caps) drives expire and graceful stop. Do not hardcode timeouts here.
- Export: `handleExportEntryEffect` → `claimCaseExportEffect` (coalesces; never start parallel case writes). The only trigger is `runActivityConsumerEffect` (core): it reads the activity log from the durable cursor row `worker-export` in `activity_cursors` (ADR-0005 S5), so a change made while the worker was down exports after the restart; a first boot starts at the head; a cursor ahead of the log (restore, wiped log) or below the retention floor (the prune job deleted entries after it) re-exports every Case (`rescanAllCasesEffect`) then resets to the head. `shouldTriggerCaseExport(entry)` is the kind and action filter: a succeeded Job, any Evidence entry and any Graph kind export; Task, Proposal, other Job actions and Case update do not (a new kind opts in there). The cursor is stored only after the claim returned, in batches, so a crash re-handles a batch (exports are idempotent) and never skips one; a defect in the claim ends the consumer and the boot (exit 1) with the cursor still before the entry. The worker has no `@watchdog/db` dependency: cursor and log reads are core's.
- Maintenance (`maintenance.ts`): core's `MAINTENANCE_TASKS` (`@watchdog/core/maintenance`) is the list of repeated jobs, each `{ name, every, failureMessage, run }` where `run` is a core Effect that succeeds with a report (`message` plus fields, logged by `emitOnce` under `name`) or `undefined` (quiet). `forkMaintenanceEffect` forks one `maintenanceLoopEffect` per task: run at boot, then after each `every` (`delayFirst` waits one spacing first, for the reconcile); a failure or defect is logged as `failureMessage` and the loop goes on. Tasks: job reconcile (`worker.reconcile`, 60 s; boot also runs one tick before the queue handler registers, and an advisory lock lets one worker reconcile), activity prune (`activity.retention`, daily; ADR-0005 S7), case purge (`case.purge.run`, #304, hourly; runs as `watchdog_app`, `SKIP LOCKED` per Case), upload sweep (`evidence.upload-sweep.run`, #305), Job start counter prune (`jobs.start-limits.prune`, #480), export archive sweep (`export.sweep.run`, #476). Boot also runs `ACTIVITY_RESTORE_CHECK` once (`activity.restore`: a restored database's future `xid`s are rewritten to 0) before the consumer starts. The worker is the one place they run: the single instance ADR-0005 assumes. What each does: [`custody`](../../docs/reference/contracts/custody.md) and the core doc comments. Add a task as one entry in core.
- Shutdown follows scope release (ADR-0002 phase 3): the first SIGTERM/SIGINT is `NodeRuntime.runMain`'s (interrupts the main fiber; the process exits **130 for SIGTERM as well as SIGINT**, as it did before this change, measured on `main`); the boot scope closes (cancel poll and LISTEN stream stop), then `jobQueueWorkerLayer` releases with a graceful `boss.stop` bounded by `gracefulStopTimeoutMs()` (in-flight Cap Jobs finish), then `JobFibers` (its finalizer stops every Job still running with `worker_shutdown`, so it ends `failed`), then core's services and finally `Db.owned`, which ends the Postgres pool (the release order is written once, in core's `coreServicesLayer`; `pool-shutdown.test.ts` records it). `main.ts` composes them through `provideWorkerLayers` (`layers.ts`): keep the queue Layer innermost. `shutdown.ts` is the `WorkerShutdown` service, its Layer provided outermost by `provideWorkerLayers` so the listeners exist from process start and outlive the drain: a repeated signal (during boot or the drain) force-exits 143 SIGTERM / 130 SIGINT, and it owns the LISTEN-failure path: the boot fails with `WorkerListenError`, the same release runs (queue drain first), and the process exits **1** (a behavior change from exit 0, so a restart-on-failure supervisor restarts the worker). A LISTEN failure during shutdown force-exits 1. `WorkerShutdown` records the first signal (`signal()`) and logs `shutting down (SIGTERM)` / `(SIGINT)` from its own release, the last to run (after the queue drain and the other services): `(interrupt)`, `(failure)` or `(exit)` appears only when no signal was seen (the queue Layer cannot see the signal, so it logs only a failed `boss.stop`). Exit codes are measured against a real worker: SIGTERM and SIGINT when idle both exit 130. Export events claim (mark dirty, start the write) in the listener fiber and fork only the wait. The detached export write fibers are in neither `JobFibers` nor the queue: shutdown does not drain them, they die with the process exactly as before, and each write owns its own `Db` / S3 client (`ExportWriteServices`), so they are not released by `provideWorkerLayers`.
- Boot: `initWatchdogLogger` first in `bootWorkerEffect`; `main.ts` runs it through `provideWorkerLayers`: core's `coreServicesLayer` over `Db.owned`, plus `JobFibers.layer` and the worker queue Layer. A reconcile tick fails stale `running` Jobs, cancels `running` Jobs whose creator lost Case access (`access_revoked`; the cancel poll stops the local fiber), re-advances playbook runs with no open Jobs, re-enqueues orphaned `queued` Jobs and rebuilds Cases whose Collect queue projection drifted (each logged as `collect_queue.drift`); a failed tick is logged and the next one tries again.
- Log failures with `log.error(err)`, never `log.set({ error: err })` (an `Error` serializes to `{}`); evlog contract in [`evlog`](../../docs/reference/contracts/evlog.md). Process wide events: `jobWideEventFields(JobRunOutcome)`.
