# Core package (`@watchdog/core`)

> Scope: `packages/core` (inherits root [AGENTS.md](../../AGENTS.md) unless noted)

Domain services for Case Graph, Jobs, Evidence, Tasks (case work items, not Graph writes), export, and vault. Talks to Postgres only through `@watchdog/db` repos; it has no `drizzle-orm` dependency, so SQL does not belong here.

## Commands

| Task              | Command                                  |
| ----------------- | ---------------------------------------- |
| Typecheck         | `pnpm --filter @watchdog/core typecheck` |
| Unit tests        | `pnpm test:unit`                         |
| Integration tests | `pnpm test:integration`                  |

## Import paths

Import from a per-domain subpath, never the root: `@watchdog/core/<domain>` where `<domain>` is `activity`, `actors`, `caps`, `cases`, `errors` (tagged errors), `evidence`, `export`, `graph` (entities, claims, edges, identifiers, questions, timeline, patch, guards), `infra` (`Db`, `tryDb`, `tryDbWith`, `transact`, `outsideTransaction`, `runDomain`, `runDomainWith`), `jobs`, `organization` (organization settings, the external AI handoff entry), `proposals`, `search`, `tasks`, `vault` (credential helpers, `Vault`, `vaultLayer`, `fakeVault`). Also `blob` (blob functions and the `BlobStore` service), `job-display`, `proposal-display` and `worker`. Each domain is `src/<domain>/index.ts`; there is no root import or `src/index.ts`. New domain: add the folder index and the `exports` entry in one change. `pnpm check:boundaries` fails an import path missing from `exports`.

## Rules

Which error tag to raise in which situation: [Error taxonomy](../../docs/reference/contracts/README.md#which-tag-to-raise).

| Rule | Enforced by |
| --- | --- |
| Services call repos with `exec: DbExec` first and own transactions (`transact`); repos never open one | `watchdog/db-repo-exec-first`, `watchdog/db-repo-no-transaction` (repo side, `pnpm check`) |
| Normalize display fields (trim, slugify, `InvalidError`) before repo writes; repos do not reject blank name/text. Trim `actorLabel` with `actorLabelForPersist` | guidance |
| Caps via catalog + `interpret` → Proposal; Caps and Jobs never write Graph directly | guidance (root Boundaries) |
| Enqueue only through `enqueueCapJobEffect` (`R = JobQueue`); never construct a `PgBoss` outside `jobs/job-queue.ts`. A process composes exactly one role Layer (`jobQueueProducerLayer` or `jobQueueWorkerLayer`) | guidance (a second `PgBoss` is not blocked by lint; `job-queue.test.ts` covers the Layers) |
| Service programs are `*Effect` and keep `DomainTag` in `E`; tests bridge with `runDomain` | `watchdog/no-effect-run-outside-edge` (`pnpm check`) for `run*` sites; the rest is guidance |
| `transact` body runs with the caller's services; interrupting the caller aborts it and rolls back; tagged errors and defects pass through unchanged; the only `run*` edge is its `runPromiseExitWith` bridge | `postgres-tx.int.test.ts`; `watchdog/no-effect-run-outside-edge` |
| A `transact` inside another `transact`'s body (or a fiber it forked) is a programmer error: it would open a second connection and transaction, commit independently and can deadlock a small pool. It dies with a defect before opening anything (`InsideTransaction` context reference set around the body; no new error tag). Pass `tx` down instead. A forked child the body awaits is still nesting (it holds a second connection while the parent waits) and dies. A DETACHED fiber (`forkDetach`) forked inside a body outlives the transaction and runs outside it: reset the flag at its root with `outsideTransaction` (`infra`; the export write fiber does), then it may run its own `transact`. A caller-provided `Db.layerOf(tx)` opens a savepoint only OUTSIDE a body; `Effect.provide(transact(...), Db.layerOf(tx))` inside a body dies with the guard | `postgres-tx.int.test.ts` |
| Inbox Accept/Reject is one `transact`: attestation + patch + status, with `proposalsRepo.lockInCase` (`FOR UPDATE`) then a re-check of `status = 'pending'` | integration tests |
| `InvalidError` is caller-fixable input (400). A write that returns no row is `InternalError`, raised only by piping the write through `requireWritten("create X")` (`infra/postgres-effect.ts`), never a hand-written `new InternalError({ reason: "Failed to …" })`; an update/delete of a caller-supplied id matching nothing is `NotFoundError({ entity, id })`; its message is derived from `entity` in the class, never hand-written. A caller-supplied string echoed in `NotFoundError.id` (an unparsed id or a slug) goes through `boundEchoedId` (trimmed, at most `MAX_ECHOED_ID_CHARS`); ids that already parsed as UUIDs are bounded by the parse; `InvalidError` and `InternalError` carry a log-only `cause` that Job failure paths log (`logJobFailureCause`); an unparseable Case id is `NotFoundError`, not `InvalidError`; a row this request just wrote and cannot read back is `InternalError` | `map-domain-error.test.ts`; no lint |
| Exported core function INPUTS take `OrganizationId` and `CaseId`, never plain strings, so a swapped `(caseId, organizationId)` call fails to compile (`src/__tests__/branded-ids.types.test.ts`, a typechecked test full of `@ts-expect-error`). The layers below carry the brands too (ADR-0003, #165): db repo `caseId` parameters, the result records (`CaseRecord.id` and the `caseId` of `EvidenceRecord`, `EntityRecord`, `JobRecord`, `ProposalRecord`, `TaskRecord`, `GraphWriteRecord`, `JobRunOutcome`) and the SSE/activity schemas are `CaseId`; the API output schemas use `caseIdSchema`, so `z.output` is branded in web and cli (`z.input` stays a string). Mint at the edge: the API parses with `caseIdSchema`/`trimmedCaseIdSchema`, the actor carries an `OrganizationId` (minted by `resolveActorOrganizationId` in `packages/auth/src/actor.ts`), other edges call `asCaseId` / `asOrganizationId`, or `parseTrimmedCaseId` for a CASE id only (every other uuid, entity/job/evidence/edge/run, uses `parseTrimmedUuid`, a plain string); never `as` (lint `watchdog/no-brand-cast`) | `pnpm typecheck`; `watchdog/no-brand-cast` |
| Case children are org-scoped: API/actor Effects take `organizationId` and gate with `assertCaseInOrgEffect` (foreign or missing Case is `not_found`). Worker/export paths that already trust a Case id use `assertCaseExistsUncheckedEffect` / `casesRepo.getByIdUnchecked`: never widen that to HTTP handlers | `org-isolation.int.test.ts` (router enumerated by `org-isolation-coverage.test.ts`) |
| Inside a TX, pass `tx` into the `assert*InCase` helpers; never assert on the global pool while writing on `tx` | guidance |

## `Db` service pattern (ADR-0002 phase 2)

`Db` (`infra/db-service.ts`) is a `Context.Service` whose value is a `DbExec`; `Db.layer` is the live Layer over `@watchdog/db`'s `db`. All core code reads the client from it: importing `db` from `@watchdog/db` in core source fails lint (`no-restricted-imports`, plus `watchdog/no-core-db-dynamic-import` for `import()`; exempt: `infra/db-service.ts` and tests). Reference: `listCasesEffect` (`cases/cases.ts`, test `cases-db-layer.int.test.ts`).

```ts
// before: R = never, module-global db
tryDb(() => casesRepo.list(db, organizationId));
// after: R = Db; same error mapping (unique violations, tagged passthrough)
tryDbWith((exec) => casesRepo.list(exec, organizationId));
```

- Add `Db` to the function's declared return type (`Effect.Effect<A, DomainTag, Db>`, `import type { Db } from "../infra/db-service"`) and drop the `db` import once no site uses it. Callers that are themselves migrated propagate `Db`; `runDomain` / `runApp` accept `R = Db` and provide `Db.layer`.
- Inside `transact((tx) => ...)` keep the explicit handle: `tryDb(() => repo.x(tx, ...))`. `transact` opens its transaction on the `Db` service's client (R gains `Db`; if the service value is itself a `tx` and the call is outside any `transact` body, drizzle opens a savepoint; inside a body it dies, see the nested-`transact` rule). Helpers that accept an optional `exec` (`assert*InCase`, `suppressKnownFindingsEffect`) use `tryDbOn(exec, ...)`: a caller's `tx` wins, otherwise the service supplies the client.
- Tests: `runDomainWith(Db.layer)(effect)` (the pool, same as `testDb`; `Db.layerOf(exec)` for a `tx` or a spying `Proxy`), or `runDomainWith(Layer.succeed(Db, stub))`. Unit tests may still `vi.mock("@watchdog/db")` (the live Layer wraps the mocked `db`); prefer the Layer. `runDomain(effect)` works for integration tests.
- Worker: `main.ts` provides `Db.layer`, `vaultLayer`, `blobStoreLayer`, `JobFibers.layer` and the worker queue Layer (`Db`, `Vault`, `BlobStore`, `JobQueue` and `jobQueueWorkerLayer` are exported from `@watchdog/core/worker`).

## `JobQueue` service pattern (ADR-0002 phase 3)

`JobQueue` (`jobs/job-queue.ts`) is the Cap Job queue as a `Context.Service`; there is no module-level boss. `enqueueCapJobEffect`, `startJobEffect`, `reconcileJobsEffect`, `advancePlaybookRunEffect`, `executeJobOnMap` and the evidence verbs that enqueue carry `JobQueue` in `R`.

- Two role Layers, each acquiring pg-boss in the Layer scope and releasing it when the scope closes. `jobQueueProducerLayer` (web/API): `supervise: false`, starts pg-boss lazily on the first send (the start runs uninterruptibly behind one gate shared with release; a failed start or ensure retries only the failed step on the next send), so building it never touches the database; release waits for an in-flight start, then stops any started boss. `jobQueueWorkerLayer` (worker): `supervise: true`, starts and ensures the queue at build (failure fails the boot), also provides `JobQueueWorker` (`work`), and releases with `boss.stop({ graceful: true, timeout: gracefulStopTimeoutMs() })`. Sends stay open during that drain (an in-flight Job may enqueue its playbook successor); after release a send fails with `InternalError`.
- A process is one role: the producer Layer does not provide `JobQueueWorker`, so worker-only code (`work`) fails to type-check against it. Composing both Layers in one process is not blocked by types (guidance).
- `runApp` / `AppLive` include the producer Layer. `runDomain` stays `Db`-only: a caller whose Effect enqueues passes a queue Layer, `runDomainWith(Layer.mergeAll(Db.layer, queue.layer))(effect)`. Tests use `recordingJobQueue()` (records sends instead of reaching pg-boss) or `makeJobQueueLayers(() => fakeDriver)` for scope-release tests; `BossDriver` is the slice of pg-boss the service uses.
- Worker: `main.ts` provides the worker queue Layer innermost so it releases (drains) before `JobFibers` closes ([`apps/worker/AGENTS.md`](../../apps/worker/AGENTS.md)).

## Readiness

`checkReadinessEffect` (`infra/readiness.ts`, exported from `@watchdog/core/infra`) is what `GET /api/v1/ready` runs: a one-row `activityFloorRepo.get` through `Db` and a `HeadBucket` through `BlobStore`, in parallel, each under `READINESS_TIMEOUT_MS`. It never fails (`E = never`): a failure or defect is `unreachable`, an expired timeout `timeout`; the driver detail goes only to `logSwallowed` / `logProcess`, so a caller never reads a host or connection string. The database ping is single-flight per pool (`WeakMap` in `readiness.ts`): the timeout interrupts the Effect, not the postgres.js query behind it, so a hung database would otherwise hold a pool connection per probe. Test with `readinessFrom({ database, storage })` and stubs (unit, `TestClock` for timeouts); the real probes are in `readiness.int.test.ts`.

## `BlobStore` service pattern (ADR-0002 phase 3)

`BlobStore` (`infra/blob-store.ts`) is the object store as a `Context.Service` of `{ client: S3Client, bucket, presignClient? }` (`presignClient` signs URLs for `S3_PUBLIC_URL`, where browsers reach the store, when it differs from `S3_ENDPOINT`; presign functions use `presignClient ?? client`); there is no module-level client. Every function in `infra/blob.ts` (`uploadArtifactEffect`, `createPresignedPutEffect`, `verifyUploadedObjectEffect`, `readArtifactBytesEffect`, `createPresignedGetEffect`, `deleteCaseArtifactsEffect`) carries `BlobStore` in `R` and maps to `InvalidError`. `R` reaches Case delete, Evidence upload/presign/download, the snapshot pack, Case export (`writeCaseExportEffect`; `scheduleCaseExportEffect` itself has `R = never`, its detached write fiber provides its own `Db` / `BlobStore`), the Cap `uploadArtifact` / `readArtifact` helpers (collect captures the service and provides it to the Cap context, whose `R` stays `never`) and `executeJobOnMap`.

- `blobStoreLayer` builds the `S3Client` from `S3_*` env when the Layer is built (no connection) and `client.destroy()`s it when the Scope closes (`Effect.acquireRelease` inside `Layer.effect`). Importing `S3Client` / `S3` from `@aws-sdk/client-s3` in core outside `infra/blob-store.ts` (static, aliased, namespace or dynamic) fails lint (`no-restricted-imports`, `watchdog/no-core-s3-dynamic-import`, gate test `oxlint-core-import-bans.gate.test.ts`); read the client with `yield* BlobStore`.
- Compose it once per process: `AppLive` (API and the web routes that use `runApp`) and the worker's `provideWorkerLayers` (outside the queue Layer, so in-flight Jobs still read blobs while the queue drains). `runDomain` provides `Db | BlobStore` (the blob Layer only builds a client, but per call, and `destroy()`s it when the call returns, so a fiber the effect forks that outlives the call must not use it; the one such fiber, the export write forked by Case update via `forkDetach`, provides its own `Db` and `BlobStore`, see the Export gotcha); a caller that needs a different store passes `runDomainWith(Layer.mergeAll(Db.layer, store.layer))`.
- Tests: `recordingBlobStore({ objects?, respond? })` is a real `S3Client` aimed at a dummy endpoint whose requests never leave the process: a middleware records each command (`calls`), serves `GetObject` / `HeadObject` / `PutObject` from an in-memory map and answers the rest through `respond`; presigning needs no network, and `destroyed()` reports the scope release. `makeBlobStoreLayer(() => ({ client, bucket }))` is the factory for any other fake; `blobStoreLayer` over the local S3 container is exercised by `infra/__tests__/blob.int.test.ts`. Do not `vi.mock` the blob module.

## `Vault` service and the clock (ADR-0002 phase 3)

Master-key rotation is `rekeyVault` (`infra/vault-rekey.ts`, all or nothing under an advisory lock, over `credentialsRepo.listAllCiphertexts` / `setCiphertext`; it takes the keys as arguments through `sealSecretWithMaster` / `openSecretWithMaster`, so the old key is never validated as a secret). The command is `src/vault-rekey-cli.ts` (`just vault-rekey`, bundled as `vault-rekey.mjs` in the web image), the one core file that reads the global `db`, because it is a process entry, not a service. Procedure: [`backup-restore`](../../docs/how-to/backup-restore.md#rotating-the-vault-key).

`Vault` (`infra/vault.ts`) is credential access as a `Context.Service` (`list`, `has`, `get`, `put`, `delete`; `get` is the only plaintext path). `listCredentialMetaEffect`, `hasCredentialEffect`, `getCredentialEffect`, `putCredentialEffect`, `deleteCredentialEffect` and the slot helpers (`listCredentialSlotsEffect`, `putCredentialSlotEffect`) carry `Vault` in `R`; the Cap availability checks, `startJobEffect`, `runPlaybookEffect` and job collect inherit it. `vaultLayer` is the live reader: it captures `Db` at build time and seals/opens with the master key (`vault-crypto.ts`), so compose it over `Db` (`Layer.provideMerge(vaultLayer, Db.layer)`) once per process, as `AppLive` and `provideWorkerLayers` do. Collect captures `Vault` and `BlobStore` and passes them into the Cap context (Cap `getCredential` / `hasCredential` / `uploadArtifact` / `readArtifact` keep R = never).

- `runDomain` provides `Db | Vault | BlobStore` (the vault Layer only captures `Db`, so it is cheap per call; the same per-call lifetime applies, see the `BlobStore` note above); `JobQueue` stays out.
- Tests: `fakeVault({ userId: { NAME: "secret" } })` (`@watchdog/core/vault`) is an in-memory `Vault` with the live name validation and `NotFoundError` (`secrets` is its map); any `Layer.succeed(Vault, Vault.of({...}))` works too. Do not `vi.mock` the vault module. Integration tests that need a real vault over the database use `Layer.provideMerge(vaultLayer, Db.layer)`. `vaultLayer` captures the `Db` it is built over, so under `runDomainWith(Db.layerOf(tx))` the live vault (from `runDomain`'s default) still uses the pool, not the `tx`: compose `Layer.provideMerge(vaultLayer, Db.layerOf(tx))` or use `fakeVault`.
- Clock: time comes from Effect's built-in `Clock`, not a new service. `infra/clock.ts` exports `nowDateEffect`, `nowMillisEffect`, `nowIsoStringEffect`; core code never calls `new Date()` for the current time (db timestamps stay `Date` values converted from the clock; expiry math adds to the clock's now). `TestClock` (`effect/testing`) drives it in tests: `TestClock.setTime` then `Effect.provide(TestClock.layer())` (`jobs/__tests__/cap-cache.int.test.ts`). Pure renderers (`export-sections.ts`) take the timestamp as a parameter. `new Date(x)` of a supplied value (parsing, repo Date interop) is fine.

## Gotchas

- Job pipeline, `JobFibers`, cancel/abort, Effect 4 sticky interrupt, boss roles, status lifecycle: [`effect/references/jobs.md`](../../.agents/skills/effect/references/jobs.md) is the single home.
- Playbooks: `advancePlaybookRunEffect` in `jobs/stages/chain.ts` is the only chain (success, failure, stale fail, stuck reclaim). `runPlaybookEffect` inserts the run and the step-0 `queued` Job; later steps are created lazily after the previous Job succeeds (`playbookFanIndex`). Do not pre-insert the rest of the recipe.
- Agent ingress: propose by default; `graph write` + `userOverride` writes Graph at `unverified` plus a `graph_writes` audit row. `parseAgentPatchEffect` is the shape gate.
- Identifier Accept validates with `validateIdentifierWrite` (same as Dossier create/update). Invalid Identifier values block Accept; `identifierCollisions` on the Inbox list only warn.
- Entity create seeds default Questions through `seedDefaultQuestionsEffect` (`graph/questions.ts`, by kind): no inline kind `if`s in `createEntity`.
- Vault slots are listed/written through the `*Effect` credential helpers (`R = Vault`) and never return plaintext.
- Organization delete: `deleteOrganizationCasesEffect(organizationId, { actorId })` tombstones (when live) and purges every Case, deleted ones included (artifacts and export dir with it), before the org row goes, because `cases.organization_id` is a soft ref and nothing cascades. The app wires it through `createAuth({ beforeDeleteOrganization })`. A purge that fails stops it with `internal`.
- Case delete is a tombstone (#304, [`custody`](../../docs/reference/contracts/custody.md#deletion-and-retention)). `cases/tombstone.ts`: `deleteCaseEffect` (owner or admin through `requireOrganizationManagerEffect` in `organization/roles.ts`, checked BEFORE the existence check (as in restore and purge) so a non-manager learns nothing about an id; one `transact` through `tombstoneInTx`: the `deleted` record and Case activity entry, then cancel queued and running Jobs and running playbook runs (`jobsRepo.cancelAllCancellableForCase`, with their `cancelled` entries), then the tombstone with `purge_after`), `restoreCaseEffect` (refused past `purge_after` and once a purge began; into a taken slug it picks `slug-2`, ... and returns `previousSlug`), `listDeletedCasesEffect` (cursor `{epoch ms}_{case id}`), `getDeletedCaseBySlugEffect` (managers only; everyone else `not_found`), `getDeletionPolicyEffect` (window, `canManage`; with a `caseId` the dialog's `cancellableJobs` count). `cases/purge.ts`: `purgeTombstonedCaseEffect` (claim with `SKIP LOCKED`, writing the `purge_started` record and `purge_started_at` the first time; delete objects, a failure is stored as `purge_error` (a `purge_failed` record when the message is new) and returned as `failed`; one transaction for the `system` history context, the `purged` record with counts and the Case delete; a second object sweep after), `purgeCaseEffect` (Purge now: needs a deleted Case, `internal` after a recorded failure, `conflict` unless the Case is gone: a skipped claim waits `FOR SHARE` and re-reads), `purgeExpiredCasesEffect` (worker run, `PURGE_BATCH` 20), `deleteOrganizationCasesEffect`. `cases/retention.ts` (`caseRetentionDays`) reads `WD_CASE_RETENTION_DAYS` (default 30) only at delete; the date is stored as `purge_after`, which `daysUntilPurge` reads. Every lifecycle change goes through `recordDeletionEventEffect` (`cases/deletion-event.ts`), which `cases_lifecycle_guard` demands (see custody). `deleteCaseArtifactsEffect` fails on any object it cannot delete (S3's per-key `Errors` included); `recordingBlobStore` is in-memory. The Cap pre-flight reads the Case once (`casesRepo.getByIdUnchecked`, which also supplies the egress switch) and cancels a Job whose Case is deleted (`case_deleted`). The pre-flight then rechecks the Job's author (`jobAccessLostReasonEffect`, `jobs/job-access.ts`, #371): the creator (`actor_id`) must still be a member of the Case's organization and not banned (`isUserBanned`), and a Job an API key started (`jobs.actor_key_id`, set from the caller's credential) needs that key to exist, belong to the creator, be enabled and not have expired (`apiKeyStatus`). A failed check cancels the Job (`access_revoked`) with the reason in its `error` (`Cancelled: the creator of this Job is no longer a member of the organization | is banned`, `Cancelled: the API key that started this Job no longer exists | was disabled | has expired`); a Playbook step cancelled this way ends its run. Each chained step Job copies the run's `actor_key_id` and is checked again; a session Job never reads the key table. The gate registry exempts the tombstone and purge functions (`graph-mutations.ts`): they write the Case, not the Graph.
- Export: `scheduleCaseExportEffect` coalesces through a `SynchronizedRef`: when the returned Effect is interpreted it marks dirty and starts-or-joins the write fiber. The write fiber is independent of the caller's lifetimes (so `R = never`): per write it builds the `ExportWriteServices` Layer (default: live `Db.layer` plus a fresh `blobStoreLayer`) and releases it after, so it never reuses a caller's rolled-back `Db.layerOf(tx)` or a per-call `S3Client` that `runDomain` destroyed. `updateCaseEffect` (`R = Db`), `claimCaseExportEffect` and `scheduleCaseExportEffect` (`R = never`) declare no `BlobStore`: the export has its own services, so `runDomainWith(...)` / `runAppWith(...)` overrides of `Db` / `BlobStore` do NOT reach it. A test that triggers `updateCaseEffect` with a name or slug change forks an export that by default writes through the REAL pool, a REAL S3 client and files under `WD_EXPORT_DIR`: provide `ExportWriteServices` (`isolatedExportWriteServices()` from `@watchdog/core/export` is the pool plus `recordingBlobStore()`; or `Effect.provideService(ExportWriteServices, Layer.mergeAll(Db.layer, recordingBlobStore().layer))`, read at claim time; see `export-sync-services.int.test.ts`) or assert it deliberately exercises the live pipeline; no setup-level default exists (it would need module state). The detached write fibers are in neither `JobFibers` nor the queue: worker shutdown does not drain them (they die with the process) each owning its `Db` / S3 client. `claimCaseExportEffect` is the first stage (mark + start, returns the wait): a caller that forks the wait claims first so an interrupt cannot lose the mark. The export dir is `<export>/<organization-id>/<case-slug>/`; a case rename regenerates the slug (unique per organization) and reschedules export.
- There are no `notify*Effect` helpers left (and no LISTEN helper but the tailer's): every domain (Tasks, Jobs, Evidence, Proposals, Graph and Case) appends to the activity log in its `transact` body and the database trigger notifies at commit. Do not add a notify call; do not call `appendActivityEffect` outside a transaction.
- Graph and Case activity (ADR-0005 S4): every Graph mutation (Entity, Edge, Claim, Identifier, timeline Event, Question), `updateCaseEffect` and each op of a patch appends one entry through `appendGraphActivityEffect(tx, ...)` (`graph/graph-activity.ts`) in the writing `transact`; a patch op appends its own (actor: the Accept reviewer or the agent), so N ops append N entries. The label is the subject's name, predicate, text or value (cut to 200); a `deleted` entry keeps it. `graph_writes`, custody provenance and idempotency are untouched. Case delete and restore append a Case-level `deleted` / `restored` entry (`kind case`, the Case as subject) in the same transaction (`recordDeletionEventEffect`), so open sessions refresh; a purge is never logged (it would cascade its entry away; `case_deletion_records` is the trace). A client on a deleted Case gets 404 on reconnect. The Graph mutation module (`graph/mutation/`) is the only Graph write path: `runGraphMutation` for Dossier writes, `runGraphMutationInTx` for patch ops. Its writer does the version check, miss handling, Evidence link and entry. A patch passes its Evidence ids as `evidenceIds` (checked once; others still checked); joined records lack `version`. The gate (`graph-activity-gate.test.ts`) fails on a write method of the six Graph repos called outside `graph/mutation/tables.ts`, except exemptions (default-Question seeding; `test-db`; demo seed); a second rule: each `casesRepo` / `tasksRepo` write is a registered `sites` entry or in `CASE_TASK_EXEMPTIONS`; `graph-activity.int.test.ts` asserts each `GRAPH_MUTATIONS` entry. Patch op `data` is decoded with Zod (`graph/patch/op-data.ts`). `GraphActor` (schemas) is the one actor object: Dossier inputs (deletes: last argument) and `ApplyPatchOpts.actor` take it. A `deleted` label comes from the row the delete returns, and a status check (Question resolve and reopen, Claim retract) lives in the UPDATE, never an earlier read: both go stale under READ COMMITTED. A Task update takes the Case then the Task row lock (`tasksRepo.lockInCase`) before it compares the status.
- Graph history (#303, [`custody`](../../docs/reference/contracts/custody.md#attribution-and-history)): triggers write `graph_history`; core only says who: `setHistoryContextEffect(tx, ctx)` (`graph/graph-activity.ts`; `dossierHistory(actor)`: no actor means channel `system`) is the FIRST statement of every Graph write transaction body, and a path that forgets it fails: the database refuses a Graph write (or Case delete) by the app role without one (SQLSTATE `WD001`, mapped by `mapPostgresCatch` to `InternalError` "Graph write without a history context"); the test harness sets no default, so a path's own tests catch it. Triage Accept and the agent write set `triage_accept` / `agent_write`; `ApplyPatchOpts.channel` is required and used when `applyPatchEffect` opens its own transaction (with a caller's `tx`, the caller sets it). Never write `created_by` / `updated_by` or insert history from core: the triggers own them. Read side: `listGraphHistoryEffect` (cursor = the last history id, `GRAPH_HISTORY_PAGE_MAX` 100; snapshots are `snake_case` in the database, camelCased out by `toWireSnapshot`).
- Activity log (ADR-0005, `@watchdog/core/activity`): `appendActivityEffect(tx, entry)` is the only writer; call it on the domain `tx` inside the `transact` body so a rollback leaves no entry. An unlisted `(kind, action)` pair (`ACTIVITY_ENTRY_ACTIONS` in `@watchdog/schemas/feed`) or a missing row is `InternalError`. Labels are cut to 200 characters and never carry bodies, patches or secrets. `ActivityTailer` (service; `activityTailerLayer` in `AppLive`, LISTEN opens on the first subscriber) feeds in-memory subscribers; `replayActivityEffect` serves `Last-Event-ID` (entries, or `resync` when the cursor is ahead of the database, below the retention floor or more than 500 entries behind); `createActivityGate` (schemas) holds live entries during a replay and drops duplicates. `runActivityConsumerEffect` (S5; exported from `@watchdog/core/worker` and `@watchdog/core/activity`) is a durable consumer: it resumes from the `activity_cursors` row of its consumer name (none means the head), a tailer started at that cursor delivers the catch-up then the live tail, `handle` runs per entry in order and the cursor is stored only after a batch was handled; a cursor ahead of the log (a restore or a wiped log) or below the retention floor calls `onResync` with every Case id and resets to the head. `FEED_ACTIONS` is the allowlist Recent activity shows (task, job, evidence `captured`, proposal `created | accepted | rejected`); `listRecentActivityEffect` reads only the log (ADR-0005 S6), so a new feed kind needs its entries appended and a label resolver, not a second source.
- Activity retention and restore (ADR-0005 S7, `activity/retention.ts`, `restore-check.ts`, `log-bounds.ts`): `pruneActivityEffect` deletes entries older than `ACTIVITY_RETENTION_DAYS` (90) in batches of `ACTIVITY_PRUNE_BATCH` (5000), keeping the newest `ACTIVITY_KEEP_PER_CASE` (200) per Case never passing the slowest durable consumer cursor that moved inside the window; every batch raises the replay floor (`activity_floor`) in the same transaction as the delete. A cursor below the floor, or above the newest position the log has held (`activityLogCeiling`: the newest row, or an emptied log's floor), is unservable (`isUnservableActivityCursor`): `replayActivityEffect` answers `resync` and `runActivityConsumerEffect` calls `onResync`, then stores `max(head, floor)` so the next boot does not resync. Never delete from `activity` elsewhere (only the Case FK cascade does). `repairRestoredActivityXidsEffect` is the boot check for a database restored from another cluster: when any `xid` is not below the cluster's next transaction id, one transaction rewrites every entry, the floor and every consumer cursor to `xid` 0. The worker runs both (`apps/worker/src/activity-maintenance.ts`).
- Job activity (ADR-0005 S2): every Job status write appends its entry (`queued`, `running` or a terminal state; label `null`, `group_id` = the playbook run) through `appendJobActivityEffect(tx, job, status)` (`jobs/job-activity.ts`) on the transaction that writes the status: `settleJobEffect`, start, cancel, the chain advance, playbook start and cancel, and `processEvidenceEffect`. Recent activity reads Job history from the log, collapsed by `group_id` in SQL (`activityLogRepo.recentFeed`), labels resolved on read (`activity/job-feed.ts`). A new path that changes a Job's status appends in the same transaction (no `notifyJobUpdateEffect`: deleted).
- Job lifecycle (`jobs/lifecycle/`, #431): `decideJob(job, event)` is the pure table over every status and event (`claim`, `succeed`, `fail`, `cancel`); a terminal Job has no move. `settleJobEffect` is the one claim, finish, fail and reclaim writer: it locks the row in its Case (`jobsRepo.lockStatus`), asks the table, and writes via `jobsRepo.settle` guarded by `allowedFromStatuses`, derived from the same table; never hand-write a status guard. `fail` and `cancel` carry a closed `JobStopCause` (`@watchdog/schemas`; CHECK on `jobs.error_code`) beside `error`. `reconcileJobsEffect` (`lifecycle/reconcile.ts`) is one worker-scheduled tick under an advisory lock (`tryLockJobReconcile`). It fails stale Jobs, cancels running Jobs failing `jobAccessLostReasonEffect` (`access_revoked`; the cancel poll stops the fiber), advances stuck playbook runs and re-enqueues orphaned queued Jobs; status changes are `settleJobEffect`s run `outsideTransaction`, so the lock lasts the tick. The cancel repo writers guard themselves until #433, #434.
- Client-safe label helpers live in `@watchdog/core/job-display`; worker code imports `@watchdog/core/worker`, not a domain subpath.
- Logging: `@watchdog/log` (`logSwallowed`, `logProcess`). evlog is not `Job.logs` / `graph_writes` custody.
- Tests: generic padded-UUID trim belongs in unit owners (`graph/patch/__tests__/guards.test.ts`, `@watchdog/schemas` `primitives-trim.test.ts`, db `scoped-ids.test.ts`); core `*.int.test.ts` assert domain contracts only. Core tests must not import `drizzle-orm`.
