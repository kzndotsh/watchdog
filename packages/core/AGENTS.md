# Core package (`@watchdog/core`)

> Scope: `packages/core` (inherits root [AGENTS.md](../../AGENTS.md) unless noted)

Domain services for Case Graph, Jobs, Evidence, Tasks (case work items, not Graph writes), export, and vault. Talks to Postgres only through `@watchdog/db` repos; no `drizzle-orm` dependency, so no SQL here.

## Commands

| Task              | Command                                  |
| ----------------- | ---------------------------------------- |
| Typecheck         | `pnpm --filter @watchdog/core typecheck` |
| Unit tests        | `pnpm test:unit`                         |
| Integration tests | `pnpm test:integration`                  |

## Import paths

Import from a per-domain subpath, never the root: `@watchdog/core/<domain>` where `<domain>` is `activity`, `actors`, `caps`, `cases`, `errors` (tagged errors), `evidence`, `export`, `graph` (entities, claims, edges, identifiers, questions, timeline, patch, guards), `infra` (`Db`, `tryDb`, `tryDbWith`, `transact`, `outsideTransaction`, `runDomain`, `runDomainWith`), `jobs`, `organization` (organization settings, the external AI handoff entry), `proposals`, `search`, `tasks`, `vault` (credential helpers, `Vault`, `vaultLayer`, `fakeVault`). Also `blob` (blob functions, `BlobStore`), `job-display`, `proposal-display`, `worker`. Each domain is `src/<domain>/index.ts`; no root import or `src/index.ts`. New domain: add the index and `exports` entry together; `pnpm check:boundaries` fails a path missing from `exports`.

## Rules

Which error tag to raise: [Error taxonomy](../../docs/reference/contracts/README.md#which-tag-to-raise).

| Rule | Enforced by |
| --- | --- |
| Services call repos with `exec: DbExec` first and own transactions (`transact`); repos never open one | `watchdog/db-repo-exec-first`, `watchdog/db-repo-no-transaction` (repo side) |
| Normalize display fields (trim, slugify, `InvalidError`) before repo writes; repos do not reject blank name/text. Trim `actorLabel` with `actorLabelForPersist` | guidance |
| Caps via catalog + `interpret` → Proposal; Caps and Jobs never write Graph directly | guidance (root Boundaries) |
| Enqueue only through `enqueueCapJobEffect` (`R = JobQueue`); never construct a `PgBoss` outside `jobs/job-queue.ts`. A process composes exactly one role Layer (`jobQueueProducerLayer` or `jobQueueWorkerLayer`) | guidance (a second `PgBoss` is not blocked by lint; `job-queue.test.ts` covers the Layers) |
| Service programs are `*Effect` and keep `DomainTag` in `E`; tests bridge with `runDomain` | `watchdog/no-effect-run-outside-edge` for `run*` sites; the rest is guidance |
| `transact` body runs with the caller's services; interrupting the caller aborts it and rolls back; tagged errors and defects pass through unchanged; the only `run*` edge is its `runPromiseExitWith` bridge | `postgres-tx.int.test.ts`; `watchdog/no-effect-run-outside-edge` |
| A `transact` inside another `transact`'s body (or a fiber it forked) is a programmer error: it would open a second connection and transaction, commit alone and can deadlock a small pool. It dies with a defect before opening anything (an `InsideTransaction` context reference around the body; no new error tag). Pass `tx` down; a forked child the body awaits is still nesting and dies. A DETACHED fiber (`forkDetach`) forked in a body outlives the transaction: reset the flag at its root with `outsideTransaction` (`infra`; the export write fiber does) and it may run its own `transact`. A provided `Db.layerOf(tx)` opens a savepoint only OUTSIDE a body; `Effect.provide(transact(...), Db.layerOf(tx))` inside a body dies with the guard | `postgres-tx.int.test.ts` |
| Inbox Accept/Reject is one `transact`: attestation + patch + status, with `proposalsRepo.lockInCase` (`FOR UPDATE`) then a re-check of `status = 'pending'` | integration tests |
| `InvalidError` is caller-fixable input (400). A write that returns no row is `InternalError`, raised only by piping the write through `requireWritten("create X")` (`infra/postgres-effect.ts`), never a hand-written `new InternalError({ reason: "Failed to …" })`; an update or delete of a caller-supplied id that matches nothing is `NotFoundError({ entity, id })`, whose message the class derives from `entity` (never hand-written). A caller string echoed in `NotFoundError.id` (an unparsed id or a slug) goes through `boundEchoedId` (trimmed, at most `MAX_ECHOED_ID_CHARS`); parsed UUIDs are bounded by the parse; `InvalidError` and `InternalError` carry a log-only `cause` that Job failure paths log (`logJobFailureCause`); an unparseable Case id is `NotFoundError`, not `InvalidError`; a row this request wrote and cannot read back is `InternalError` | `map-domain-error.test.ts`; no lint |
| Exported core function INPUTS take `OrganizationId` and `CaseId`, never plain strings, so a swapped `(caseId, organizationId)` call fails to compile (`src/__tests__/branded-ids.types.test.ts`). The layers below carry the brands too (ADR-0003, #165): db repo `caseId` parameters, result records (`CaseRecord.id`, the `caseId` of `EvidenceRecord`, `EntityRecord`, `JobRecord`, `ProposalRecord`, `TaskRecord`, `GraphWriteRecord`, `JobRunOutcome`) and the SSE/activity schemas are `CaseId`; API output schemas use `caseIdSchema`, so `z.output` is branded in web and cli (`z.input` stays a string). Mint at the edge: the API parses with `caseIdSchema`/`trimmedCaseIdSchema`, the actor carries an `OrganizationId` (`resolveActorOrganizationId`, `packages/auth/src/actor.ts`), other edges call `asCaseId` / `asOrganizationId`, or `parseTrimmedCaseId` for a Case id only (every other uuid, entity/job/evidence/edge/run, uses `parseTrimmedUuid`, a plain string); never `as` (lint `watchdog/no-brand-cast`) | `pnpm typecheck`; `watchdog/no-brand-cast` |
| Case children are org-scoped: API/actor Effects take `organizationId` and gate with `assertCaseInOrgEffect` (foreign or missing Case is `not_found`). Worker/export paths that already trust a Case id use `assertCaseExistsUncheckedEffect` / `casesRepo.getByIdUnchecked`: never widen that to HTTP handlers | `org-isolation.int.test.ts` (router enumerated by `org-isolation-coverage.test.ts`) |
| Inside a TX, pass `tx` into the `assert*InCase` helpers; never assert on the global pool while writing on `tx` | guidance |

## `Db` service pattern (ADR-0002 phase 2)

`Db` (`infra/db-service.ts`) is a `Context.Service` of a `DbExec`; `Db.owned` is the process's one owner of the Postgres pool (#443): a scoped Layer whose release ends the client (`POOL_END_TIMEOUT_SECONDS`) and clears the HMR slot. `Db.layer` borrows the pool without ending it (`runDomain`, tests, the export write fiber); `Db.ownedBy(open)` is the test seam; `sharedDb()` lends it outside Effects (web's Better Auth). Core reads the client from `Db`: importing `db`, `client`, `acquirePool`, `endPool`, `createPool` or `withPool` from `@watchdog/db` fails lint (`no-restricted-imports`; `watchdog/no-core-db-dynamic-import` for `import()`; exempt: `db-service.ts`, `vault-rekey-cli.ts`, tests). Reference: `listCasesEffect` (`cases/cases.ts`; test `cases-db-layer.int.test.ts`).

```ts
casesRepoFxDb.list(organizationId); // R = Db; DomainTag errors
```

- Repo calls (`infra/repo-fx.ts`, `repos-fx.ts`, #444/#445): `xRepoFx.m(exec, ...)` is the method as `Effect<T, DomainTag>`; `xRepoFxDb.m(...)` is the pool form (`R = Db`); `onExec(exec, (h) => xRepoFx.m(h, ...))` serves a helper with an optional handle (a caller's `tx` wins). Never wrap a repo call in `tryDb`/`tryDbWith` (`watchdog/no-repo-wrapper`); the one exception passes `opts` (`uniqueIndex`, `conflictReason`; the mapping needs the raw driver error): `tryDb(() => repo.m(tx, ...), opts)`. Otherwise `tryDb`/`tryDbWith` wrap non-repo driver calls. A generic or overloaded method does not map (types widen): hand-write it beside the module. Add repos to `repos-fx.ts` as used.
- Add `Db` to the declared return type (`Effect.Effect<A, DomainTag, Db>`, `import type { Db } from "../infra/db-service"`) and drop the `db` import once unused. Callers propagate `Db`; `runDomain` / `runApp` provide `Db.layer`.
- Inside `transact((tx) => ...)` keep the explicit handle: `xRepoFx.m(tx, ...)`. `transact` opens its transaction on the `Db` service's client (R gains `Db`; a service value that is itself a `tx`, outside any `transact` body, opens a savepoint; inside a body it dies: see the nested-`transact` rule). Helpers with an optional `exec` (`assert*InCase`, `suppressKnownFindingsEffect`) use `onExec(exec, ...)`.
- Tests: `runDomainWith(Db.layer)(effect)` (the pool, as `testDb`; `Db.layerOf(exec)` for a `tx` or spying `Proxy`) or `runDomainWith(Layer.succeed(Db, stub))`. Unit tests may `vi.mock("@watchdog/db")` (`Db.layer` reads its `acquirePool`); prefer the Layer. `runDomain(effect)` works in integration tests.
- Worker: `main.ts` provides `Db.owned` (ends last), `vaultLayer`, `blobStoreLayer`, `JobFibers.layer` and the worker queue Layer (exported from `@watchdog/core/worker`: `Db`, `Vault`, `BlobStore`, `JobQueue`, `jobQueueWorkerLayer`).

## `JobQueue` service pattern (ADR-0002 phase 3)

`JobQueue` (`jobs/job-queue.ts`) is the Cap Job queue as a `Context.Service`, with no module-level boss. `enqueueCapJobEffect`, `startJobEffect`, `reconcileJobsEffect`, `advancePlaybookRunEffect`, `executeJobOnMap` and the evidence verbs that enqueue carry `JobQueue` in `R`.

- Two role Layers, each acquiring pg-boss in the Layer scope and releasing it when the scope closes. `jobQueueProducerLayer` (web/API): `supervise: false`, starts pg-boss lazily on the first send (uninterruptible, behind one gate shared with release; a failed start or ensure retries only the failed step on the next send), so building it never touches the database; release waits for an in-flight start, then stops a started boss. `jobQueueWorkerLayer` (worker): `supervise: true`, starts and ensures the queue at build (failure fails the boot), provides `JobQueueWorker` (`work`) and releases with `boss.stop({ graceful: true, timeout: gracefulStopTimeoutMs() })`. Sends stay open during that drain (an in-flight Job may enqueue its Playbook successor); after release a send is `InternalError`.
- A process is one role: the producer Layer does not provide `JobQueueWorker`, so worker-only code (`work`) fails to type-check against it. Composing both Layers in one process is not blocked by types (guidance).
- `runApp` / `AppLive` include the producer Layer. `runDomain` is `Db`-only: a caller that enqueues passes a queue Layer, `runDomainWith(Layer.mergeAll(Db.layer, queue.layer))(effect)`. Tests use `recordingJobQueue()` (records sends, no pg-boss) or `makeJobQueueLayers(() => fakeDriver)` (scope release); `BossDriver` is the pg-boss slice the service uses.
- Worker: `main.ts` provides the worker queue Layer innermost so it drains before `JobFibers` closes ([`apps/worker/AGENTS.md`](../../apps/worker/AGENTS.md)).

## Readiness

`checkReadinessEffect` (`infra/readiness.ts`, exported from `@watchdog/core/infra`) is what `GET /api/v1/ready` runs: a one-row `activityFloorRepo.get` through `Db` and a `HeadBucket` through `BlobStore`, in parallel, each under `READINESS_TIMEOUT_MS`. It never fails (`E = never`): a failure or defect is `unreachable`, an expired timeout `timeout`; the driver detail goes to `logSwallowed` / `logProcess` only, never to a caller (no host or connection string). The database ping is single-flight per pool (`WeakMap` in `readiness.ts`): the timeout interrupts the Effect, not the postgres.js query behind it, so a hung database would hold a pool connection per probe. Unit-test with `readinessFrom({ database, storage })` stubs (`TestClock` for timeouts); real probes: `readiness.int.test.ts`.

## `BlobStore` service pattern (ADR-0002 phase 3)

`BlobStore` (`infra/blob-store.ts`) is the object store, a `Context.Service` of `{ client: S3Client, bucket, presignClient? }` (`presignClient` signs URLs for `S3_PUBLIC_URL`, where browsers reach the store, when it differs from `S3_ENDPOINT`; presign functions use `presignClient ?? client`). Every function in `infra/blob.ts` (`uploadArtifactEffect`, `createPresignedPutEffect`, `verifyUploadedObjectEffect`, `readArtifactBytesEffect`, `createPresignedGetEffect`, `deleteCaseArtifactsEffect`) carries `BlobStore` in `R` and maps to `InvalidError`. `R` reaches Case delete, Evidence upload/presign/download, snapshot pack, Case export (`writeCaseExportEffect`; `scheduleCaseExportEffect` is `R = never`, see Export), the Cap `uploadArtifact` / `readArtifact` helpers (collect captures the service for the Cap context, whose `R` stays `never`) and `executeJobOnMap`.

- `blobStoreLayer` builds the `S3Client` from `S3_*` env when the Layer is built (no connection) and `client.destroy()`s it when the Scope closes (`Effect.acquireRelease`). Importing `S3Client` / `S3` from `@aws-sdk/client-s3` in core outside `infra/blob-store.ts` (static, aliased, namespace or dynamic) fails lint (`no-restricted-imports`, `watchdog/no-core-s3-dynamic-import`, gate test `oxlint-core-import-bans.gate.test.ts`); read the client with `yield* BlobStore`.
- Compose it once per process: `AppLive` and the worker's `provideWorkerLayers` (outside the queue Layer, so in-flight Jobs still read blobs while the queue drains). `runDomain` provides `Db | BlobStore` (the blob Layer builds a client per call and `destroy()`s it when the call returns, so a fiber it forks that outlives the call must not use it; the one such fiber, Case update's export write (`forkDetach`), provides its own `Db` and `BlobStore`, see the Export gotcha); a caller needing another store passes `runDomainWith(Layer.mergeAll(Db.layer, store.layer))`.
- Tests: `recordingBlobStore({ objects?, respond? })` is a real `S3Client` aimed at a dummy endpoint whose requests never leave the process: a middleware records each command (`calls`), serves `GetObject` / `HeadObject` / `PutObject` from an in-memory map and answers the rest through `respond`; presigning needs no network, and `destroyed()` reports the scope release. `makeBlobStoreLayer(() => ({ client, bucket }))` is the factory for any other fake; `infra/__tests__/blob.int.test.ts` runs `blobStoreLayer` over the local S3 container. Never `vi.mock` the blob module.

## `Vault` service and the clock (ADR-0002 phase 3)

Master-key rotation is `rekeyVault` (`infra/vault-rekey.ts`, all or nothing under an advisory lock, over `credentialsRepo.listAllCiphertexts` / `setCiphertext`; it takes the keys as arguments through `sealSecretWithMaster` / `openSecretWithMaster`, so the old key is never validated as a secret). The command is `src/vault-rekey-cli.ts` (`just vault-rekey`, bundled as `vault-rekey.mjs` in the web image), a process entry: it opens and ends the pool through `withPool`. Procedure: [`backup-restore`](../../docs/how-to/backup-restore.md#rotating-the-vault-key).

`Vault` (`infra/vault.ts`) is credential access as a `Context.Service` (`list`, `has`, `get`, `put`, `delete`; `get` is the only plaintext path). `listCredentialMetaEffect`, `hasCredentialEffect`, `getCredentialEffect`, `putCredentialEffect`, `deleteCredentialEffect` and the slot helpers (`listCredentialSlotsEffect`, `putCredentialSlotEffect`) carry `Vault` in `R`, as do the Cap availability checks, `startJobEffect` / `runPlaybookEffect` and the collect stage. `vaultLayer` is the live reader: it captures `Db` at build time and seals/opens with the master key (`vault-crypto.ts`), so compose it over `Db` (`Layer.provideMerge(vaultLayer, Db.layer)`) once per process, as `AppLive` and `provideWorkerLayers` do. Collect captures `Vault` and `BlobStore`, so Cap `getCredential` / `hasCredential` / `uploadArtifact` / `readArtifact` keep `R = never`.

- `runDomain` provides `Db | Vault | BlobStore` (the vault Layer only captures `Db`: cheap per call, same lifetime note as `BlobStore`); `JobQueue` stays out.
- Tests: `fakeVault({ userId: { NAME: "secret" } })` (`@watchdog/core/vault`) is an in-memory `Vault` with the live name validation and `NotFoundError`; any `Layer.succeed(Vault, Vault.of({...}))` works too. Do not `vi.mock` the vault module. `vaultLayer` captures the `Db` it is built over, so under `runDomainWith(Db.layerOf(tx))` the live vault (from `runDomain`'s default) still uses the pool, not the `tx`: compose `Layer.provideMerge(vaultLayer, Db.layerOf(tx))` or use `fakeVault`.
- Clock: time comes from Effect's built-in `Clock`, not a new service. `infra/clock.ts` exports `nowDateEffect`, `nowMillisEffect`, `nowIsoStringEffect`; core code never calls `new Date()` for the current time (db timestamps stay `Date` values converted from the clock; expiry math adds to its now). `TestClock` (`effect/testing`) drives it in tests: `TestClock.setTime`, then `Effect.provide(TestClock.layer())` (`jobs/__tests__/cap-cache.int.test.ts`). Pure renderers (`export-sections.ts`) take the timestamp as a parameter. `new Date(x)` of a supplied value (parsing, repo interop) is fine.

## Gotchas

- Job pipeline, `JobFibers`, cancel/abort, Effect 4 sticky interrupt, boss roles, status lifecycle: [`effect/references/jobs.md`](../../.agents/skills/effect/references/jobs.md) is the single home.
- Playbooks: `advancePlaybookRunEffect` (`jobs/stages/chain.ts`) is the only chain (success, failure, stale fail, stuck reclaim; sets the outcome on finish). `runPlaybookEffect` inserts the run and the step-0 `queued` Job; later steps are created lazily (`playbookFanIndex`), never pre-inserted. A failed step skips only its dependents; only a user cancel abandons a run. A retry of a run's Job rejoins it under the run lock (`retry-resume.ts`).
- Agent ingress: propose by default; `graph write` + `userOverride` writes Graph at `unverified` plus a `graph_writes` audit row. `parseAgentPatchEffect` is the shape gate.
- Identifier Accept validates with `validateIdentifierWrite` (same as Dossier create/update). Invalid Identifier values block Accept; `identifierCollisions` on the Inbox list only warn.
- Entity create seeds default Questions through `seedDefaultQuestionsEffect` (`graph/questions.ts`, by kind): no inline kind `if`s in `createEntity`.
- Vault slots go through the `*Effect` credential helpers (`R = Vault`), never plaintext.
- Organization delete: `deleteOrganizationCasesEffect(organizationId, { actorId })` tombstones (when live) and purges every Case, deleted ones included (artifacts and export dir with it), before the org row goes, because `cases.organization_id` is a soft ref (nothing cascades). The app wires it through `createAuth({ beforeDeleteOrganization })`. A purge that fails stops it with `internal`.
- Case delete is a tombstone (#304, [`custody`](../../docs/reference/contracts/custody.md#deletion-and-retention)). `cases/tombstone.ts`: `deleteCaseEffect` (owner or admin, `requireOrganizationManagerEffect`, checked before existence, as in restore and purge, so a non-manager learns nothing about an id; one `transact` through `tombstoneInTx`: the `deleted` record and Case activity entry, then `cancelWithin` (`case_deleted`) and the Playbook runs, then the tombstone with `purge_after`; `afterCommit` runs after the `transact`), `restoreCaseEffect` (refused past `purge_after` or once a purge began; a taken slug becomes `slug-2`, ..., `previousSlug` returned), `listDeletedCasesEffect` (cursor `{epoch ms}_{case id}`), `getDeletedCaseBySlugEffect` (managers only, else `not_found`), `getDeletionPolicyEffect` (window, `canManage`; with a `caseId`, the dialog's `cancellableJobs` count). `cases/purge.ts`: `purgeTombstonedCaseEffect` (claim with `SKIP LOCKED`, writing the `purge_started` record and `purge_started_at` once; delete objects, a failure is stored as `purge_error` (a `purge_failed` record when the message is new) and returned as `failed`; one transaction for the `system` history context, the `purged` record with counts and the Case delete; then a second object sweep), `purgeCaseEffect` (Purge now: needs a deleted Case; `internal` after a recorded failure; `conflict` unless the Case is gone), `purgeExpiredCasesEffect` (worker, `PURGE_BATCH` 20), `deleteOrganizationCasesEffect`. `cases/retention.ts` (`caseRetentionDays`) reads `WD_CASE_RETENTION_DAYS` (default 30) only at delete; the date is stored as `purge_after` (`daysUntilPurge`). Every lifecycle change goes through `recordDeletionEventEffect` (`cases/deletion-event.ts`), as `cases_lifecycle_guard` demands (see custody). `deleteCaseArtifactsEffect` fails on any object it cannot delete; The Cap pre-flight reads the Case once (`casesRepo.getByIdUnchecked`, also the egress switch), cancels a deleted Case's Job (`case_deleted`), runs `evaluateCapAvailabilityEffect` (egress, credentials, `breach_disabled` while `breachCapsEnabled()` / `WD_BREACH_CAPS=off`; start-job, `ensurePlaybookRunnable` and process-evidence ask the same; a failure ends the Job `preflight_failed`), then rechecks the Job's author (`jobAccessLostReasonEffect`, `jobs/job-access.ts`, #371): the creator (`actor_id`) must still be a member and not banned (`isUserBanned`); a Job an API key started (`jobs.actor_key_id`, from the caller's credential) needs that key to exist, be the creator's, enabled and unexpired (`apiKeyStatus`). A failed check cancels the Job (`access_revoked`), reason in `error` (`Cancelled: the creator of this Job is no longer a member of the organization | is banned`; `Cancelled: the API key that started this Job no longer exists | was disabled | has expired`); a Playbook step cancelled so ends its run. Each chained step Job copies the run's `actor_key_id` and is rechecked. The gate registry exempts the tombstone and purge functions (`graph-mutations.ts`).
- Export: `scheduleCaseExportEffect` coalesces through a `SynchronizedRef`: once interpreted it marks dirty and starts or joins the write fiber. The write fiber outlives its caller (`R = never`): per write it builds `ExportWriteServices` (default: live `Db.layer` plus a fresh `blobStoreLayer`), then releases it, never a rolled-back `Db.layerOf(tx)` or a destroyed `runDomain` `S3Client`. `updateCaseEffect` (`R = Db`), `claimCaseExportEffect` and `scheduleCaseExportEffect` (`R = never`) declare no `BlobStore`: the export has its own services, so `runDomainWith` / `runAppWith` overrides of `Db` / `BlobStore` do not reach it. A test whose `updateCaseEffect` changes a name or slug forks an export that writes through the REAL pool, S3 client and `WD_EXPORT_DIR` by default: provide `ExportWriteServices` (`isolatedExportWriteServices()` from `@watchdog/core/export`: the pool plus `recordingBlobStore()`; or `Effect.provideService(ExportWriteServices, Layer.mergeAll(Db.layer, recordingBlobStore().layer))`, read at claim time; see `export-sync-services.int.test.ts`) or exercise the live pipeline on purpose (no setup default). The detached write fibers are in neither `JobFibers` nor the queue: shutdown does not drain them. `claimCaseExportEffect` is the first stage (mark + start, returns the wait): a caller forking the wait claims first, so an interrupt cannot lose the mark. The export dir is `<export>/<organization-id>/<case-slug>/`; a rename regenerates the slug (unique per organization) and reschedules.
- No `notify*Effect` or LISTEN helper exists but the tailer's: every domain (Tasks, Jobs, Evidence, Proposals, Graph, Case) appends to the activity log in its `transact` body and the database trigger notifies at commit. Add no notify call; never call `appendActivityEffect` outside a transaction.
- Graph and Case activity (ADR-0005 S4): every Graph mutation (Entity, Edge, Claim, Identifier, timeline Event, Question), `updateCaseEffect` and each op of a patch appends one entry through `appendGraphActivityEffect(tx, ...)` (`graph/graph-activity.ts`) in the writing `transact`; a patch op appends its own (actor: the Accept reviewer or the agent): N ops, N entries. The label is the subject's name, predicate, text or value; a `deleted` entry keeps it. `graph_writes`, custody provenance and idempotency are untouched. Case delete and restore append a Case-level `deleted` / `restored` entry (`kind case`) in the same transaction (`recordDeletionEventEffect`), so open sessions refresh; a purge is never logged (its entry would cascade away; `case_deletion_records` is the trace). A client on a deleted Case gets 404 on reconnect. The Graph mutation module (`graph/mutation/`) is the only Graph write path (`runGraphMutation` for Dossier writes, `runGraphMutationInTx` for patch ops); its writer does the version check, miss handling, Evidence link and entry. A patch passes its Evidence ids as `evidenceIds` (checked once; others still checked); joined records lack `version`. The gate (`graph-activity-gate.test.ts`) fails on a write method of the six Graph repos called outside `graph/mutation/tables.ts` (exempt: default-Question seeding, `test-db`, demo seed), and on a `casesRepo` / `tasksRepo` write that is neither a registered `sites` entry nor in `CASE_TASK_EXEMPTIONS`; `graph-activity.int.test.ts` asserts each `GRAPH_MUTATIONS` entry. Patch op `data` is decoded with Zod (`graph/patch/op-data.ts`). `GraphActor` (schemas) is the one actor object: Dossier inputs (deletes: last argument) and `ApplyPatchOpts.actor` take it. A `deleted` label comes from the row the delete returns, and a status check (Question resolve and reopen, Claim retract) lives in the UPDATE, never an earlier read: both go stale under READ COMMITTED. A Task update takes the Case then the Task row lock (`tasksRepo.lockInCase`) before comparing the status.
- Graph history (#303, [`custody`](../../docs/reference/contracts/custody.md#attribution-and-history)): triggers write `graph_history`; core only says who: `setHistoryContextEffect(tx, ctx)` (`graph/graph-activity.ts`; `dossierHistory(actor)`: no actor means channel `system`) is the FIRST statement of every Graph write transaction body: the database refuses a Graph write (or Case delete) by the app role without one (SQLSTATE `WD001`, mapped by `mapPostgresCatch` to `InternalError` "Graph write without a history context"); the harness sets no default, so a path's own tests catch it. Triage Accept and the agent write set `triage_accept` / `agent_write`; `ApplyPatchOpts.channel` is required, used when `applyPatchEffect` opens its own transaction (a caller's `tx` sets its own). Never write `created_by` / `updated_by` or insert history from core: the triggers own them. Read side: `listGraphHistoryEffect` (cursor: last history id, `GRAPH_HISTORY_PAGE_MAX` 100; snapshots are `snake_case` in the database, camelCased by `toWireSnapshot`).
- Activity log (ADR-0005, `@watchdog/core/activity`): `appendActivityEffect(tx, entry)` is the only writer; call it on the domain `tx` inside the `transact` body, so a rollback leaves no entry. An unlisted `(kind, action)` pair (`ACTIVITY_ENTRY_ACTIONS` in `@watchdog/schemas/feed`) or a missing row is `InternalError`. Labels are cut to 200 characters; never bodies, patches or secrets. `ActivityTailer` (`activityTailerLayer` in `AppLive`; LISTEN opens on first subscribe) feeds subscribers; `replayActivityEffect` serves `Last-Event-ID` (entries, or `resync` when the cursor is ahead of the database, below the floor or over 500 entries behind); `createActivityGate` (schemas) holds live entries during a replay, dropping duplicates. `runActivityConsumerEffect` (S5; from `@watchdog/core/worker` and `@watchdog/core/activity`) is a durable consumer: it resumes from its consumer's `activity_cursors` row (none: the head), a tailer started there delivers catch-up then live tail, `handle` runs per entry in order and the cursor is stored only after a batch was handled; a cursor ahead of the log (restore, wiped log) or below the floor calls `onResync` with every Case id and resets to the head. `FEED_ACTIONS` is the allowlist Recent activity shows (task, job, evidence `captured`, proposal `created | accepted | rejected`); `listRecentActivityEffect` reads only the log (S6): a new feed kind needs entries and a label resolver, no second source.
- Activity retention and restore (ADR-0005 S7, `activity/retention.ts`, `restore-check.ts`, `log-bounds.ts`): `pruneActivityEffect` deletes entries older than `ACTIVITY_RETENTION_DAYS` (90) in batches of `ACTIVITY_PRUNE_BATCH` (5000), keeping the newest `ACTIVITY_KEEP_PER_CASE` (200) per Case and never passing the slowest durable consumer cursor that moved inside the window; each batch raises the replay floor (`activity_floor`) in the delete's transaction. A cursor below the floor, or above the newest position the log has held (`activityLogCeiling`: the newest row, or an emptied log's floor), is unservable (`isUnservableActivityCursor`): `replayActivityEffect` answers `resync` and `runActivityConsumerEffect` calls `onResync`, then stores `max(head, floor)` so the next boot does not resync. Never delete from `activity` elsewhere (only the Case FK cascade does). `repairRestoredActivityXidsEffect` is the boot check for a database restored from another cluster: when any `xid` is not below the cluster's next transaction id it rewrites every entry, the floor and each consumer cursor to `xid` 0 in one transaction. The worker runs both (`activity-maintenance.ts`).
- Job activity (ADR-0005 S2): every Job status write appends its entry (`queued`, `running` or a terminal state; label `null`, `group_id` = the playbook run) through `appendJobActivityEffect(tx, job, status)` (`jobs/job-activity.ts`) on the transaction that writes the status: `settleJobEffect` (cancel too), start, the chain advance, playbook start and `processEvidenceEffect`. Recent activity reads Job history from the log, collapsed by `group_id` in SQL (`activityLogRepo.recentFeed`), labels resolved on read (`job-feed.ts`). A new status-changing path appends in the same transaction. A Playbook run finishing appends `playbook_run` `finished` (#456) in `advancePlaybookRunEffect`'s finish transaction (`subject_id` and `group_id` the run, `to_value` the outcome, label `null`); not a feed kind, no export.
- Job lifecycle (`jobs/lifecycle/`, #431): `decideJob(job, event)` is the pure table over every status and event (`claim`, `succeed`, `fail`, `cancel`); a terminal Job has no move. `settleJobEffect` is the one claim, finish, fail, cancel and reclaim writer: it locks the row in its Case (`jobsRepo.lockStatus`), asks the table, and writes via `jobsRepo.settle` guarded by `allowedFromStatuses` (derived from the same table; never hand-write a status guard). `fail` and `cancel` carry a closed `JobStopCause` (`@watchdog/schemas`; CHECK on `jobs.error_code`) beside `error`. `run(jobId, { cap, system })` is the worker's one settle (`acquireUseRelease`: claim and preflight, the Cap or system body, uninterruptible release by Exit); abort sources offer a `JobStop` to its first-writer-wins stop slot (`JobFibers.abort`). Each terminal outcome runs `advancePlaybookTailEffect` when its settle moved the Job (else the canceller does); a success (reclaimed too) caches and stamps Evidence. `reconcileJobsEffect` is a worker tick under an advisory lock (`tryLockJobReconcile`): it fails stale Jobs, cancels running Jobs failing `jobAccessLostReasonEffect` (`access_revoked`), advances stuck runs and re-enqueues orphaned queued Jobs, settling `outsideTransaction` so the lock lasts the tick. Sources outside a transaction use `stop(selector, cause, detail?)`; the API cancel and Case delete use `cancelWithin(tx, selector, cause)`, whose `afterCommit` (abort fibers, advance runs) runs post-commit ([`jobs.md`](../../.agents/skills/effect/references/jobs.md)). Only this module writes Job status (`job-status-only-in-lifecycle`). System Jobs (Case export): [`jobs-orpc`](../../docs/reference/platform/jobs-orpc.md#system-jobs-and-case-export).
- Client-safe label helpers live in `@watchdog/core/job-display`; worker code imports `@watchdog/core/worker`, not a domain subpath.
- Logging: `@watchdog/log` (`logSwallowed`, `logProcess`). evlog is not `Job.logs` / `graph_writes` custody.
- Tests: generic padded-UUID trim belongs in unit owners (`graph/patch/__tests__/guards.test.ts`, `@watchdog/schemas` `primitives-trim.test.ts`, db `scoped-ids.test.ts`); core `*.int.test.ts` assert domain contracts only. Core tests must not import `drizzle-orm`.
