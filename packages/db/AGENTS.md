# Database package (`@watchdog/db`)

> Scope: `packages/db` (inherits root [AGENTS.md](../../AGENTS.md) unless noted)

Drizzle ORM + postgres.js for the Watchdog Case Graph and Better Auth tables.

## Commands

| Task | Command |
| --- | --- |
| Repo rules | `pnpm check` (oxlint `watchdog/db-repo-*`, scoped to `src/repos/*.repo.ts`) |
| Generate / apply migrations | `pnpm db:generate` · `pnpm db:migrate` (the owner role: `DATABASE_URL_MIGRATE`; also installs pg-boss's schema and regrants `watchdog_app`) |
| Studio | `pnpm db:studio` |
| Wipe case data | `just wipe` / `just wipe yes`: truncates public Graph/Jobs/Inbox/Evidence (including `graph_history`: the script opts in to its guarded TRUNCATE for the transaction); keeps `auth.*` (users, orgs, members, API keys), `credentials`, and migrations. Also empties the evidence bucket when the local `watchdog-s3` container is running and `S3_ENDPOINT` is local. Not `docker compose down -v`. |
| Screenshot seed | `just seed-demo` · `just seed-demo --force`: fictional cases in `scripts/demo-seed/`, owned by the earliest org owner; leaves no queued Jobs. |

## Structure

| Layer | Location | Owns |
| --- | --- | --- |
| Model | `src/schema/*` | Table definitions |
| Repository | `src/repos/*.repo.ts` | SQL only: queries/commands over `DbExec` (`src/exec.ts`) |
| Barrel | `src/repos/index.ts` | Named re-exports, entrypoint `@watchdog/db` (`@watchdog/db/schema` for schema-only) |

Services (`@watchdog/core`) call repos; controllers (`@watchdog/api`) call services. Apps never write SQL, except `@watchdog/auth`; the SSE route reaches Postgres through core (the `ActivityTailer`). The barrel is re-exports only: no aggregate `repos` object (it would pull every repo into any importer's graph). Repos take `exec: DbExec` first (the `Db` handle outside a TX, `tx` inside) so multi-table units of work such as Inbox Accept stay one transaction.

## Repo contract

| # | Rule | Enforced by |
| --- | --- | --- |
| 1 | Rows, not DTOs: no `.toISOString()`, no API-shaped objects. Display read-model joins are fine (`…Row` / `…With…`), nested, never flattened | `watchdog/db-repo-no-dto-date` (`toISOString`); nesting is review |
| 2 | Never send a NOTIFY (`pg_notify`, `.notify(`) from a repo. The only sender is the `activity` log's `AFTER INSERT` trigger, so the signal is part of the transaction (delivered at commit, dropped on rollback) | `watchdog/db-repo-no-notify` |
| 3 | Never throw domain errors; return `null` / `[]` and let the service decide 404 vs conflict. Unique-violation mapping lives in core (`tryDb` / `mapPostgresCatch`) | `watchdog/db-repo-no-throw` |
| 4 | Never open a transaction; only services call `transact` | `watchdog/db-repo-no-transaction` |
| 5 | Plain values only: no `SQL` / `eq(...)` in public signatures | `watchdog/db-repo-no-sql-param` |
| 6 | Soft delete is the repo's job: `evidence` and `cases` have `deletedAt`; exclude deleted by default and name methods that bypass the predicate by one scheme: `*IncludingDeleted` reads in any state (`getUriInCaseIncludingDeleted`, `getByIdIncludingDeleted`), `*Deleted*` touches tombstones only and takes `tombstonedCase`. Every read of `cases`, and every join that scopes by Case, takes `visibleCase` (`src/repos/_visible-case.ts`) | review; `src/repos/__tests__/cases.repo.int.test.ts` |
| - | No local job status set: use `OPEN_` / `CANCELLABLE_` / `LIVE_` / `TERMINAL_JOB_STATUSES` from `@watchdog/schemas` | `watchdog/db-repo-no-job-status-set` |
| - | Builder API only: no raw `sql` template fragments (existing ones are baselined per file; shrink, never raise) | `watchdog/db-repo-no-raw-sql` |
| - | No `zod` / `drizzle-zod` import: repos do not validate | `watchdog/db-repo-no-validation-import` |
| - | Leading `exec: DbExec` parameter; no `trimmedOrNull` in repos; `trimmedOrUndefined` only in lookup-only methods | `watchdog/db-repo-exec-first`, `watchdog/db-repo-no-trim-or-null`, `watchdog/db-repo-trim-lookup-only` |

Repos do **not** re-validate display strings (name/title/text, slugify, blank→null): Zod and core `*Effect` own that. Repos do keep lookup scoping (`trimCaseId` / `trimResourceId` / `trimActorId` on WHERE; an invalid UUID returns `[]` / `null`), slug WHERE keys (`slugForLookup`; case slugs are unique per organization, so case-by-slug lookups take `organizationId`), fail-closed graph ids, and actor integrity on proposals. `create`/`update` return `null` for a scoped-id miss, actor reject, or zero-row update/delete, not for empty display text. Padded-UUID lookup behavior is tested once in `src/repos/__tests__/scoped-ids.test.ts`.

Trimming boundary (ADR-0003): a `CaseId` is already a validated uuid, so for a typed Case id the repos' `trimCaseId` / `trimScopedCaseIds` have nothing left to clean up and stay as a fail-closed re-check: a brand stamped without validation (`untrustedCaseId`, tests only) still misses instead of matching. The helpers themselves still trim plain strings (`trimCaseId("  <uuid>  ")` returns the `CaseId`, and `orgCaseFilter` accepts padded canonical UUIDs), which is what the padded-UUID tests exercise. `_scoped-ids.ts` is the one place a plain string enters: `trimCaseId(string)`, `trimResourceId(string)` (entity, job, evidence, edge, proposal and other graph ids stay plain strings until their own phase) and `trimActorId`. A test that passes a padded or malformed Case id on purpose parses it at the test edge with `untrustedCaseId(...)` from `@watchdog/schemas/testing`; it never casts and never loosens a repo signature back to `string`.

## Schema conventions (guidance; nothing lints these)

- Enums: `text().$type<T>()` from `@watchdog/schemas`, never `pgEnum`. JSONB: concrete `$type` interfaces, no bare `jsonb()`.
- Builder API only (`select` / `insert` / `update` / `delete`); no `db.query` / `relations()`.
- Branded ids: every `case_id` / `cases.id` column is `.$type<CaseId>()` and every organization id column (`cases.organization_id`, `auth.organization.id`, `member`, `invitation`, `session.active_organization_id`) is `.$type<OrganizationId>()`. That is a promise the database cannot check: raw `sql` results are not branded. Repo `organizationId` and `caseId` parameters (and the `caseId` of every `values` / input object) are `OrganizationId` / `CaseId`; a swapped `(caseId, organizationId)` call fails to compile. `cases.repo` takes its Case id as `CaseId` too. Never cast.
- PKs: `uuid().defaultRandom()` for domain tables, `text` for Better Auth. Timestamps: `src/schema/_helpers.ts`. Postgres owns `updated_at` (BEFORE UPDATE trigger `touch_updated_at`, `0017`, on every `public` table with the column; a new table with one attaches it in its migration), so never set `updatedAt` in `.set()`. `src/__tests__/table-classification.int.test.ts` makes every `public` table a record (`created_at`, `updated_at`, trigger), append-only (`created_at`, no UPDATE for the app role), an Evidence link (`created_at`) or exempt with a reason: a new table fails it until listed.
- Vocabulary CHECKs: every column typed from a vocabulary tuple gets `vocabCheck(t.col, TUPLE)` (`src/schema/_vocab.ts`) in its table's constraints, which generates `CHECK (col IN (...))` named `<table>_<column>_vocab`. `src/schema/vocab-checks.ts` (`vocabChecks()`) lists them; `src/__tests__/vocabulary-checks.int.test.ts` compares each with the constraint Postgres holds, so a value added to a tuple needs its migration. A new vocabulary column needs a `vocabCheck` and a valid-row builder in that test.
- Same-Case keys: a row that hangs off an Entity (`claims`, `identifiers`, `events`, `questions`), an Edge, and every Evidence link table carries `case_id` and composite foreign keys `(x_id, case_id)` into `unique (id, case_id)` on the parent (`entities`, `claims`, `identifiers`, `edges`, `evidence`, `proposals`, `jobs`). Repo `create` and `link*` / `replace*` take the `caseId`. An Entity's `ON DELETE SET NULL` on `evidence.entity_id` / `tasks.entity_id` needs the column list `("entity_id")` (Postgres 15+, hand-added in `0001_database_logic`: drizzle cannot spell it, and `same-case-integrity.int.test.ts` reads `confdelsetcols` so a regeneration that loses it fails), otherwise it would null `case_id` too. The Evidence end of `proposal_evidence` / `job_evidence` is `RESTRICT` (forensic); the `cases` BEFORE DELETE trigger `evidence_links_before_case_delete` keeps a Case delete working.
- Evidence ids of Proposals and Jobs: `proposal_evidence` / `job_evidence` (ordered by `position`), never a JSON column. `ProposalRow.evidenceIds` and `JobRow.evidenceIds` are folded into the row's own statement by `src/repos/_evidence-ids.ts` (a correlated array subquery, no extra round trip: raw `sql` by necessity, because the builder cannot express it, and the helper sits in an underscore file outside the `*.repo.ts` scope of `watchdog/db-repo-no-raw-sql` for the same reason); `jobsRepo.create` / `update` and `proposalsRepo.create` write the links. Statement budgets: `packages/core/src/__tests__/custody-hot-path-queries.int.test.ts`.
- Indexes in array callback form; every foreign key gets an index that leads with its column (`src/__tests__/fk-indexes.int.test.ts` fails on one without it): Postgres scans the child table on each parent delete otherwise. A partial index does not count unless its predicate is implied by the lookup (`jobs.playbook_run_id`). Drop an index that is a strict prefix of another.
- Migrations: the TypeScript schema is the source. `pnpm db:generate` then `pnpm db:migrate`; never hand-author a migration without its `drizzle/meta` snapshot (keep it in sync with `_journal.json`). `CREATE SCHEMA "auth"` migrations use `IF NOT EXISTS` when `init.sql` already created it (a hand edit of `0000_baseline`, line 1).
- Constraining an existing column: additive first (a new column nullable, a new table), then a `--custom` backfill when rows exist, then the constraint, then the drop. The migrator applies all pending migrations in one transaction, so a refusal leaves the database as it was, and `NOT VALID` + `VALIDATE` would not shorten the lock. A hand edit of generated SQL (statement order, a column list) keeps its snapshot; say so in the file's header comment.
- Migration workflow: generate with an explicit name, `pnpm db:generate --name=<what_changed>` (snake_case, e.g. `add_task_due_date`); never accept a random drizzle name. A released migration (anything on `main`) is immutable: never edit or rename it, add a new one. The one exception (#500) squashed everything into `0000_baseline` and `0001_database_logic` (custom: every function and trigger, and the two `SET NULL (entity_id)` keys); it is not a precedent. Functions and triggers are not in drizzle's snapshot: change one with a new `--custom` migration holding `CREATE OR REPLACE FUNCTION`. `pnpm check:migrations` (pre-commit, CI) runs generate and fails when a schema edit has no migration.
- Migrations at runtime (container image): `src/migrate.ts` (`runMigrations`, `withMigrationLock`) applies the `drizzle/` folder with drizzle-orm's migrator, which shares `drizzle.__drizzle_migrations` and the journal with `drizzle-kit`, under a session advisory lock (`MIGRATION_LOCK_KEY`) on a single-connection client. `src/migrate-cli.ts` is its CLI (`DATABASE_URL_MIGRATE`, else `DATABASE_URL`; `WD_MIGRATIONS_DIR`; exit 1 on failure), bundled by `pnpm --filter @watchdog/db build:migrate` into `dist/migrate.mjs`; `pnpm db:migrate` runs the same CLI through tsx, so dev, CI and the image all take the steps below. drizzle-kit stays the dev tool for `generate`; a migration must work under both.
- **Two roles** (`src/app-role.ts`): the owner (`DATABASE_URL_MIGRATE`) owns every object and runs migrations, the first-admin command and vault rotation; the app connects as `watchdog_app` (`APP_ROLE`, created by `docker/postgres/` init, never by a migration) with SELECT, INSERT, UPDATE, DELETE on tables and USAGE, SELECT on sequences in `public`, `auth` and `pgboss`, no CREATE, no ownership, no TRUNCATE, TRIGGER or REFERENCES. After the drizzle migrations, in the same lock and as the owner, `runMigrations` installs or upgrades pg-boss's schema (`src/job-queue-schema.ts`; the app starts pg-boss with `migrate: false`, so nothing at runtime needs DDL) and calls `applyAppRoleGrants` (skipped when the role does not exist): revoke CREATE, regrant every table and sequence, set `ALTER DEFAULT PRIVILEGES FOR ROLE <owner>` so tables a later migration creates are usable at once, and revoke UPDATE, DELETE, TRUNCATE, TRIGGER and REFERENCES on the `AUDIT_TABLES` that exist (`graph_writes`, `case_deletion_records`, `provider_calls`, `provider_call_outcomes`, `evidence_provider_calls`, `finding_suppressions`, and `graph_history` as read-only; a table not created yet is skipped, so add a new append-only table to that one list); callable DEFINER functions: `APP_FUNCTIONS`). The revocations cannot live in a migration, because default privileges re-grant UPDATE and DELETE to each new table. A new migration needs no grants. Tests connect as `watchdog_app` too and wipe tables through an owner client (`resetTestDb` in `@watchdog/test-db`); `src/__tests__/app-role.int.test.ts` is the proof. `docker/smoke.sh` repeats it. Entrypoint and kill switch: [`self-host`](../../docs/how-to/self-host.md).
- `drizzle.config.ts` does not use `@watchdog/env/server`: it loads the repo-root `.env` with dotenv.
- **Soft refs (no FK):** `jobs.proposal_id` (cycles with `proposals.job_id`) · `claims.superseded_by_claim_id` / `proposals.superseded_by_proposal_id` (self-ref) · `cap_cache.job_id` (cache may outlive the Job; `case_id` is a real FK) · `credentials.user_id` and `cases.organization_id` (Better Auth ids as text, no cross-schema FK).

## Gotchas

- Case tombstone (#304): `cases.deleted_at` / `deleted_by` (+ `purge_after`, `purge_started_at`, `purge_error`) mark a deleted Case. `visibleCase` (`deleted_at IS NULL`) is the one predicate: `casesRepo` list, `listIds`, `listAllIdsUnchecked`, `search`, `getById`, `getByIdUnchecked`, `lockById`, `getBySlug`, `update`, `orgCaseFilter` (the feed and the org-scoped replay) and `entitiesRepo.getWithCase` all take it; a new reader of `cases` takes it too, or says in its name that it does not (`*IncludingDeleted`: any state, e.g. `getByIdIncludingDeleted(exec, id, org, { lock })`; `*Deleted*`: tombstones only, with the twin predicate `tombstonedCase`, e.g. `getDeletedBySlug`, `lockDeletedForPurge`, `purgeDeleted`). `casesRepo.tombstone` / `restoreDeleted` are UPDATEs (a restore is refused while `purge_started_at` is set, and may set a new slug); `casesRepo.purgeDeleted` deletes only a tombstone and the Case's foreign keys cascade through the Graph, `graph_history`, Evidence, Jobs and the activity log (as the table owner: `watchdog_app` need not delete `graph_writes` itself). Core sets the `system` history context first (#352). `cases_organization_id_slug_uidx` is a partial unique index over visible Cases (`WHERE deleted_at IS NULL`), so a deleted Case does not hold its slug. `case_deletion_records` (`caseDeletionRecordsRepo`: `append`, `listForCase`, `countPurgeContent`) is append-only by privilege, has no foreign key to `cases` and holds one row per `deleted`, `restored`, `purge_started`, `purge_failed` and `purged` event, each with an `xid` (the writing transaction) that `cases_lifecycle_guard` (`0001_database_logic`, WD002) compares: for `watchdog_app` a lifecycle change of a Case, or its DELETE, needs the matching record written first in the same transaction (the owner is exempt: the maintenance path); `just wipe`, run as the owner, empties it with the rest.
- Evidence uploads (#305): `evidence_uploads` (`evidenceUploadsRepo`) holds one row per presigned object key (`unique (case_id, uri)`, cascade with the Case): the declared hash, type and size, the asker, `created_at` (a repeat presign restarts it) and `confirmed_at` (set in the transaction that records the Evidence). `lockAbandoned` is the sweep's read (`FOR UPDATE SKIP LOCKED`, unconfirmed, older than the cutoff, no Evidence row holding the key); the caller deletes the objects before `deleteByIds` in the same transaction. Not audit: the app role may update and delete it. Seed helpers: `backdateEvidenceUpload`, `listEvidenceUploadUris`.
- Collect's queue projection (#574): [`collect-queue`](../../docs/reference/platform/collect-queue.md).
- Legacy feeds (#299): only the activity-log repo takes an optional `{ limit, after }`; every other list is declared (below). A feed method orders by its sort columns then `id` in one direction; the condition is `keysetAfter({ idColumn, keys, direction, after })` from `src/repos/_keyset.ts` (raw `sql` lives there, outside `*.repo.ts`, like `_evidence-ids.ts`). Mark a timestamp key `time: true` and select `keyTime: timeKey(column)` beside the row: the cursor carries that text (microseconds), and the next page compares against it, never a re-read of the row, so an updated or deleted row cannot move the cursor. Each paged list has an index that leads with its scope column and ends with the sort key and id (`evidence_case_captured_idx`, `cases_organization_name_idx`, ...; descending ones are `DESC NULLS FIRST` so a plain `ORDER BY ... DESC` can use them); the case-wide Identifier list sorts across a join and has none. Tests: `src/repos/__tests__/keyset.int.test.ts`.
- `listenOnChannel` opens a dedicated postgres.js connection that stays open until `end()`: awaiting `sql.listen` only waits for LISTEN to start, so ending the connection behind it silently drops every notification (ADR-0005 S1; consumers keep a fallback poll). Its only caller is the activity tailer, on `watchdog_activity`.
- Activity retention (ADR-0005 S7): `activity_floor` is a one-row table (`singleton` boolean primary key with a check) holding the newest `(xid, id)` ever pruned; `activityFloorRepo.get` / `raise` (forward only, `setWhere` row comparison) / `zeroXid`. `activityLogRepo.pruneBatch(exec, { before, keepPerCase, limit, notPast })` is the only prune: it deletes in `(xid, id)` order rows older than `before`, outside the newest `keepPerCase` of their Case (by id, through `(case_id, id desc)`: the boundary is probed once per Case in a CTE, and the probe says `NULLS LAST` because a bare `DESC` is an order that index cannot give), at or below `notPast`, and returns `{ count, newest }` (a candidate SELECT, then a DELETE by id; a data-modifying CTE cannot be `EXPLAIN`ed); the caller (core) runs it and `activityFloorRepo.raise` in one `transact`. `activityCursorsRepo.slowestActive(exec, since)` is the lowest cursor among consumers that moved at or after `since`.
- Activity cursors (ADR-0005 S5): `activity_cursors(consumer, xid, id)` holds one durable read position per named consumer (`activityCursorsRepo.get` / `set`, upsert in either direction so a resync can move a stale cursor back to the head); the worker export consumer is the only user. `createActivityTailer` takes `startAt` (resume after a cursor instead of the head) and `onListenError` (a LISTEN that could not connect, apart from drain errors the tailer survives). `casesRepo.listAllIdsUnchecked` is the worker re-scan read.
- Row version (#307): the six Graph tables (entities, edges, identifiers, claims, events, questions; not `tasks`) carry `version integer not null default 1` (`rowVersion` in `src/schema/_helpers.ts`), bumped by the BEFORE UPDATE trigger `graph_version_bump`, never by a repo or a caller; `graph_history_row` ignores it like `updated_at`. A repo's `updateInCase(exec, caseId, id, patch, expectedVersion?)` adds `AND version = $n` (`atVersion`, `src/repos/_version.ts`) and returns `null` for a miss (core re-reads to tell stale from gone); an empty patch with a version still runs as a touch (`setOrTouch`). `lockAtVersionInCase` (claims, identifiers, edges) takes the row's lock only at the expected version, for an edit that also replaces Evidence links (their trigger touch bumps the version). Reads return `version` in every `*Columns`. Contract: [`custody`](../../docs/reference/contracts/custody.md#optimistic-concurrency).
- Attribution and history (#303): every Graph table and `tasks` carries `created_by` / `updated_by` (user id as text, no FK; `NULL` is unknown). Both are filled by the BEFORE trigger `graph_attribution` from the transaction's `watchdog.actor_id` setting, never by a repo: repo `New*` / `*Patch` types do not carry them. `graph_history` is written only by the triggers of `0001_database_logic` (`graph_history_row` on the seven Graph tables, `graph_history_link_changed` on the Evidence link tables), as the table owner (`SECURITY DEFINER`); the app role has `SELECT` only. `graphHistoryRepo` is read-only (`listForRow`). `setGraphHistoryContext(tx, { actorId, actorLabel, actorKeyId, channel })` (`src/history-context.ts`, not a repo) sets the four transaction-local settings (`actor_key_id` is the API key's id on `graph_history` and `activity`; `isUserBanned` in `src/auth/user-ban.ts` is the ban check for API keys) the triggers read; core calls it first in every Graph write transaction, and the BEFORE trigger `graph_history_context_guard_trg` (function `graph_require_history_context`, SQLSTATE `WD001`, `HISTORY_CONTEXT_MISSING_SQLSTATE` in `@watchdog/schemas/shared`) refuses a write by `watchdog_app` on the Graph tables, the Evidence link tables and a Case delete when `watchdog.channel` is unset or empty (the owner is never refused and records `system`; a cascade runs as the owner). Any script or job that writes the Graph as the app role calls `setGraphHistoryContext` first (the demo seed does); repository tests use `withSystemTestTx` / `withSystemHistoryContext` from test-db. The guard trigger refuses UPDATE, DELETE while the Case exists, and TRUNCATE (unless `SET LOCAL watchdog.allow_history_truncate = 'on'`: `just wipe` and the owner-run `resetTestDb` / `resetE2eDb` do). Every trigger function pins `search_path = pg_catalog, pg_temp` and qualifies `public.`: keep both in any new one. Evidence-link replaces write only the difference (`notInArray` delete, `onConflictDoNothing` insert), so re-saving the same set records nothing. `applyAppRoleGrants` lists `graph_history` as a read-only audit table (SELECT only for `watchdog_app`). Never add the table to a prune job. A single-superuser install is not tamper-resistant (see [`custody`](../../docs/reference/contracts/custody.md#attribution-and-history)).
- Activity log (ADR-0005): table `activity` (`id bigint identity`, `xid xid8 default pg_current_xact_id()`), the only writer is `activityLogRepo.append(tx, ...)` through core's `appendActivityEffect`. The custom migration `0001_database_logic` installs the `activity_notify` trigger, which `pg_notify`s `watchdog_activity` with `{id, caseId}` (a wake-up; readers fetch rows). Read only through `activityLogRepo.drain`: `(xid, id) > cursor AND xid < pg_snapshot_xmin(pg_current_snapshot())`, which never returns a row that an older still-open transaction could precede. `createActivityTailer` is the per-process tailer (one LISTEN connection, a 5 s fallback poll, a 250 ms re-poll while a transaction holds rows back). Backfilled rows carry `xid = 0`. An `xid8` restored from another cluster can sit in the future: core's boot check rewrites it (`activityLogRepo.hasFutureXid` / `zeroXids`, `activityFloorRepo.zeroXid`, `activityCursorsRepo.zeroXids`; see [`restore-database`](../../docs/how-to/restore-database.md)).
- Jobs: `retry_of_job_id` (self FK, `on delete set null`, indexed) links a retry to the finished Job it repeats; null for a first attempt. Unique `(playbook_run_id, playbook_step, playbook_fan_index)` on first attempts only (`jobs_playbook_run_step_fan_uq`, partial on `retry_of_job_id IS NULL`: a retry of a step is a further attempt in the same slot; `jobs_playbook_run_updated_idx` serves the foreign key); `playbook_runs.outcome` (nullable, CHECK `playbook_runs_outcome_vocab`: `succeeded | partial | failed`, set by `playbookRunsRepo.finish`, cleared by `reopen`); new steps insert `queued`; `jobs.error_code` (nullable, CHECK `jobs_error_code_vocab`) holds the `JobStopCause` of a `failed` or `cancelled` Job and `error` its detail. The `actor_label` columns store an API-key display snapshot (`api-key:…`) only; `actor_id` stays the user id. `jobs.actor_key_id` and `playbook_runs.actor_key_id` (#371) hold the starting API key's id (no FK, null for a session): chained steps copy the run's, and the Job pre-flight reads it through `apiKeyStatus` (`src/auth/api-key-status.ts`: `usable | missing | disabled | expired`, a key owned by someone else is `missing`).
- Provider calls (#495): `provider_calls` (the request side, inserted before a call is sent: `providerCallsRepo.insertRequest`), `provider_call_outcomes` (how it ended, one row per call: `insertOutcome`) and `evidence_provider_calls` (Evidence to the calls behind it: `linkEvidence`). All three are append-only by privilege (`AUDIT_TABLES`), every insert is `ON CONFLICT DO NOTHING` (a repeated save is a no-op), and the repo has no update or delete. `provider_calls.id` is assigned by the Job's ledger (a UUID), `(job_id, run_id, seq)` is unique, and `case_id` rides in composite keys: `(job_id, case_id)` to `jobs` (cascade), `(call_id, case_id)` from the outcome (cascade) and the link (RESTRICT, like the Evidence end), `(evidence_id, case_id)` from the link (RESTRICT). A Case delete works because the `evidence_links_before_case_delete` trigger is `SECURITY DEFINER` (pinned `search_path`, like `graph_history`'s) so it can clear `evidence_provider_calls`, a table the application role cannot delete from. `provider_call_outcomes.body_state` has a shape CHECK (`none` has no hash, blob or reason; `stored` has a blob key and a hash; `hashed` a reason and no blob; `partial` a reason) written as implications on known states, so an unknown value is refused by its vocabulary CHECK alone. `served_from_call_id` is a soft reference (no FK): an in-process feed cache can serve a Job in another Case. `jobs.provenance_state` (`complete | incomplete`) flags a gap in a Job's record; `jobs.cache_source_job_id` (soft reference, like `cap_cache.job_id`) names the Job whose cached result a hit reused. `countPurgeContent` counts calls, outcomes, links and `providerRawBodies` (outcomes holding a blob key). The read side (#498): `listForJob` and `listForEvidence` (each call with its outcome and its Job's Cap, version and `provenance_state`, optional `limit`), `getInCase`, `findIdsInCase` and `listCacheHits`. A soft reference is resolved only by a lookup that carries the Case (`findIdsInCase`, and the `cache_source` self-join in `listCacheHits`), so a row of another Case is absent from the answer. Core's save path: [`caps-boundary`](../../docs/reference/platform/caps-boundary.md#outbound-http). Tests: `src/__tests__/provider-calls.int.test.ts`, and the role proofs in `app-role.int.test.ts`.
- Tasks: `position` int NOT NULL; column order is `position, id` (`listColumn`); write it through `nextPosition` / `rewriteOrder`.

- Declared lists (ADR-0007, #549): a list declared in `@watchdog/schemas` is bound to SQL once with `defineListRepo(def, binding)` (`src/repos/_list-query.ts`; one `src/repos/*-list.repo.ts` per list), builder API only. The binding maps every filter to a predicate, every sort to a NOT NULL column of the list's table whose type matches the declared key (a nullable one only as `{ column, nullsAs: '' }`), and every search field to a column of the table; a missing or mistyped one does not compile (`src/repos/__tests__/list-binding.types.test.ts`). `base(exec, listKey)` selects the row, its display joins and `listKey`; filters and search read the list's table only, so `countCapped` counts it without the joins. The repo gives `page`, `countCapped` and `byIds`; WHERE, ORDER BY and the cursor value all read one `KeysetOrder` (keyset v2 in `_keyset.ts`). Each sort has a btree led by the scope column and ending in the id; a `selective` filter has one led by its column (or the scope column, then it); a `selectiveEither` filter (the Connection list's `entityId`, at `from_id` or `to_id`) has one led by each column; the search fields have `gin_trgm_ops` indexes (`pg_trgm`, migration `0002`). All are declared in `src/schema/*.ts`. `LIST_REPOS` (`@watchdog/db/testing`) lists every binding for core's `list-conformance*.int.test.ts`. Declared lists read only through these repos; `identifiersRepo.listForEntity` (Entity export) and `listWithValues` (Inbox collisions, one `text[]` param via `textInAny`) are not lists.
- Postgres `53300` is usually Vite/tsx HMR leaking pools: restart vite + worker. The main pool (`src/client.ts`) lives in one `globalThis.__watchdogPool` slot (the HMR guard): `acquirePool()` returns it or opens one, `endPool()` ends it (bounded by `POOL_END_TIMEOUT_SECONDS`) and clears the slot so a later acquire opens a fresh pool, never a dead client. `withPool(use)` is for one-shot process entries. Only the owner Layer (`Db.owned` in `@watchdog/core`) and those CLIs import these; `db` / `client` stay exported for tests and `@watchdog/test-db` and are lint-banned in production code.

- `job_start_limits` (an organization's override with `key_id` NULL, or an API key's; FKs to `auth.organization` and `auth.apikey` with `on delete cascade`; no row means the `WD_JOB_START_LIMIT_*` default) and `job_start_counters` (starts per `scope` + `subject_id` + `window_start`, no FKs). `jobStartCountersRepo.take` is the atomic admit: one `INSERT ... ON CONFLICT DO UPDATE SET count = count + 1 WHERE count < limit`, so concurrent starts at the limit cannot both pass; the window start is the database clock floored to the window (`_job-start-window.ts`, where the raw `sql` lives), and a subject's first start of a window deletes its earlier rows. `jobStartLimitsRepo` reads (`forStart`, `listForOrganization`), upserts and clears overrides, `keyOrganization` resolves the organization a key acts in as `createApiContext` does (metadata, else the owner's oldest membership; `resolveUserOrganizationId`), and `jobStartCountersRepo.pruneEnded` deletes ended windows in batches (worker: `job-start-prune.ts`, hourly).
