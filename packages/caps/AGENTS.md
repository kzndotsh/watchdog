# Caps package (`@watchdog/caps`)

> Scope: `packages/caps` (inherits root [AGENTS.md](../../AGENTS.md) unless noted)

Cap implementations, the registry, Playbooks, and the Cap SPI (`@watchdog/caps/sdk`, `src/sdk/`). Caps never write the Graph: `interpret` returns Proposal ops only, and **Triage Accept** (or Dossier) applies them. New Cap: load `/create-cap`. Naming, layers, and ship gates D1–D5: [`caps-lexicon`](../../docs/reference/platform/caps-lexicon.md).

## Commands

| Task                    | Command                                  |
| ----------------------- | ---------------------------------------- |
| Typecheck (src + tests) | `pnpm --filter @watchdog/caps typecheck` |
| Regen catalog           | `pnpm generate:caps`                     |
| Cap unit tests          | `pnpm test:unit`                         |

## Rules

| Rule | Enforced by |
| --- | --- |
| `run` returns an Effect (`CapRun`: `Effect<CapRunResult, ToolsTag, CapServices>`; `ToolsTag` is the only vendor error family, and `runCap` rethrows the tag itself); `interpret(report, opts)` is pure/sync and returns Proposal ops. Cap I/O on `CapContext` (`uploadArtifact`, `getCredential`, `readArtifact`, …) is Effect | types (`src/sdk/define.ts`) |
| A `ValidationVendorError` raised in a Cap carries a fixed message; its `cause` is logged server-side, so it holds upstream diagnostics only (status, error class), never the caller's input (URL, email, IOC) or free upstream or model text that can echo it (use `upstreamDiagnostic`); the message reaches clients and Job failure text. Covered for `extract.ai`, `media.oembed` and `wayback.fetch`; the other Caps are guidance | `run.test.ts` / `fetch-error.test.ts` |
| Secrets via `ctx.getCredential`; never in `Job.input` or logs. Caps have no `@watchdog/db` dependency | `package.json` + knip for the dependency; the rest is guidance |
| A Cap's worker lane derives from its descriptor (`capLane`: `act` kind is `act`, `process` kind or `slow` flag is `heavy`, else `quick`); set `lane` only to override. An `act` Cap runs at most once per Job (it starts from `queued` only; a lost attempt is failed by reconcile, never re-run), so it need not be idempotent | `src/sdk/__tests__/lane.test.ts`; core `act-once.int.test.ts` |
| A Cap that reads user-supplied bytes passes a limit to `ctx.readArtifact(uri, { maxBytes, reason })` (the refusal is a `ValidationVendorError` with the fixed `reason`, and the object is never loaded in full); `eml.analyze` and `file.analyze` do. No other Cap reads an artifact | `blob-store.test.ts` (core), the two `run.test.ts` |
| Set `timeoutMs` on the Cap; it drives abort/expire/stale reclaim, so do not hardcode those timeouts in worker/core | guidance |
| A Cap has no authored version: `version` in `capabilities.gen.json` is a SHA-256 fingerprint (12 hex) of the modules the Cap's `cap.ts` reaches, written by `pnpm generate:caps` (`src/cap-fingerprint.ts`). The crawl follows imports to the module that defines each symbol (a barrel is looked through, so one vendor edit moves only its own Caps), counts `@watchdog/schemas` and the lockfile version of each npm package a reached module imports, and skips generated files, `__tests__`, type-only imports and the shared transport files of `packages/tools/src/http` (`safe-fetch`, `capped-body`, `outbound-*`, `http-client-layer`, `redirect`, `blocked-address`, `abort-when`, `transport-error`, `egress*`, `call-observer`, `body-tap`, `provider-call`, `redact-url`); the logic files there (`fetch-json`, `http-probe*`, `unshorten`, `page-enrich`, `oembed`, ...) count. The version keys the result cache; core reads it through `capVersion` (`@watchdog/caps`) | `src/__tests__/capabilities-gen.test.ts` recomputes it, so `pnpm test` fails on a stale catalog; `src/__tests__/cap-fingerprint.test.ts` |
| Never hand-edit `capabilities.gen.json` or `docs/reference/platform/cap-register.md`; run `pnpm generate:caps` | CI drift job (`ci.yml`), `src/__tests__/cap-register.test.ts` |
| Every Cap has a `provider` (shared constants in `src/providers/`), read from the provider's own terms; `commercialUse: "unknown"` when they are unclear or unreachable, never a guess; `attribution` only where the terms require credit | type (`CapabilityDef.provider`); the verdicts are reviewed by hand |
| Every fixed host a Cap declares has a reviewed redistribution verdict in `HOST_REDISTRIBUTION` (`src/redistribution.ts`): `allowed` only where the provider's own text lets a private Case Export carry its raw responses to a client (the stricter recipient; publishing, resale and feeding another lookup service are out of scope), else `unknown` or `forbidden` (both withhold). Never a guess; the owner reviews them by hand like `commercialUse`, quoting the deciding text | `redistribution.test.ts` (a declared host with no entry, or an entry for no declared host, fails) |
| Every Cap declares `contacts` (required; `contact.provider`, `.download`, `.target`, `.dnsZone`, `.model` from `src/sdk/contacts.ts`; `[]` for a Cap that stays on the install) and has no `egress` field: its egress classes derive from them (`deriveEgressClasses`, `@watchdog/schemas/caps`), and a Case must allow each before a Job runs ([`caps-lexicon`](../../docs/reference/platform/caps-lexicon.md#contacts-and-egress-classes)). A new Cap adds a case to `src/__tests__/declaration/` (it runs under a recording `Egress` with refusal on, `createRecordedRun({ policy: egressPolicyFor(cap.contacts, input) })`, the policy a Job builds, and fails on a refused call, a host its contacts do not admit or a contact no run used: `undeclaredHosts`, `unusedContacts` in `src/testing`; a Job's `Egress` refuses any request the contacts do not admit, on every redirect hop, and a download that is not a body-less GET of its fixed URL, so fix a refusal by correcting the declaration, never the policy; `contact.target("http", { anyHost: true })` only for a Cap that makes one call per redirect hop) and its classes to `cap-egress-classes.test.ts` | type (`CapabilityDef.contacts`); `src/__tests__/contacts-declaration.test.ts`, `src/__tests__/cap-egress-classes.test.ts` |
| State a fact once: `flags` holds `slow` / `invasive` only (`needs_key` derives from `credentials`, `third_party` and the egress classes from `contacts`), `reportLabel` defaults to the id, and the user agent is the `{ userAgent }` that `defineCollectCap` hands to `fetch` | type; `watchdog/no-derived-cap-metadata` |
| A Cap under `breach/` is a breach Cap (`isBreachCap`, derived flag `breach`; never authored): off until `WD_BREACH_CAPS=safe` or `full`, enforced in core at availability, start-job, preflight and Playbook start ([`caps-lexicon`](../../docs/reference/platform/caps-lexicon.md#breach-caps-are-opt-in)); `checkCapabilityAvailability` / `checkPlaybookAvailability` take `breachCapsEnabled`, so a new caller must pass it | type (`AvailabilityOpts`); `src/__tests__/breach-category.test.ts`; core `breach-opt-in.int.test.ts` |
| What a Job stores of a Cap's provider response bodies is `capBodyPolicy(cap)` (`src/sdk/raw-response.ts`): kept up to the default keep limit, or to the Cap's own `rawResponse: { keep: { maxBytes } }`; over the limit the hash and size stay and the body is withheld. `rawResponse: { keep: "hash_only" }` keeps no body, and a `breach.*` Cap is always hash-only (derived from the id, whatever it declares), as are model calls (at the door). The hash, size, status and allowlisted headers are always recorded | `src/sdk/__tests__/raw-response.test.ts`; core `provider-calls.int.test.ts` (a breach Cap stores no body) |
| Playbook ids are kebab-case and the first token equals `seedKinds[0]`; Cap ids keep dots | `src/playbooks/__tests__/naming.test.ts` (ids), nothing for Cap ids |
| Inside `playbooks/`, import Caps from `../registry`, not the `@watchdog/caps` barrel | guidance |
| Every Collect Cap has `__tests__/interpret.test.ts`; mock HTTP with `@watchdog/test-kit/http`, never `msw` | guidance |
| A Wayback CDX lookup never reports a failure as no captures: a 429 is retried once only when `Retry-After` is at most 5 s, and a longer wait, a second 429, or an HTML body where JSON is expected fails the Job (`RateLimitedError`, or a `ParseVendorError` that says the archive answered with a page); the shared `fetchJson` 429 retry is off there because it waits as long as the header says, which can outlast `timeoutMs`. `archive.wayback.lookup` lists distinct versions by default (`collapse=digest`), takes `after` / `before` as `YYYY`, `YYYY-MM` or `YYYY-MM-DD` (inclusive: `after` from the start of the period, `before` to its end), keeps 200 and `-` captures, and returns a `resumeKey` when it was cut | `packages/tools/src/wayback/__tests__/cdx-versions.test.ts`, `date-bounds.test.ts` |
| `archive.page.history` is bounded because every version is one request to a shared archive: `maxVersions` defaults to 10 and is at most 25, fetches run one at a time 500 ms apart, each body is cut at 1 MiB (`bodyTruncated`), and no fetch starts unless it and the final uploads still fit in the Job: the window runs from the start of the run (CDX calls included) to `timeoutMs` less one fetch timeout and an upload reserve, both derived in `versions.ts`. Evidence is faithful: each capture is fetched in `id_` mode and stored byte for byte (`rawSha256`). Only a comparison copy is decoded (header charset, then `<meta>`, then UTF-8) and stripped of known Wayback injections (matched on an element's own `src` / `href` host, `id` / `class` and the toolbar comment block, never on inline script text); its hash (`contentHash`) drives dedupe, because CDX digests can differ for the same page, and the change summary. A failed fetch is listed in `failed` and the rest are kept; after a 429 the remaining fetches are skipped (`skipped_rate_limited`); a run that stored nothing fails instead of reporting an empty history; a capped capture count carries `totalCapturesIsLowerBound` | `page.history/__tests__/run.test.ts`, `strip.test.ts` |
| Tools (`@watchdog/tools`) own producer Zod and fetch/parse; Caps import those schemas from `@watchdog/tools/<domain>` subpaths (never re-export them), own artifact upload and `interpret` | guidance |

## Gotchas

- `identity.pgp.lookup` asks five HTTPS keyservers; the list and which query kinds each answers is `PGP_KEYSERVERS` in `@watchdog/tools/identity`, and the Cap's `contacts` and `dataSource` derive from it. A new keyserver also needs a `pgpKeyserverProviders` entry (`src/providers/identity.ts`) and an `unknown` verdict in `HOST_REDISTRIBUTION`; `identity.pgp.lookup/__tests__/contacts.test.ts` fails otherwise.
- `core` imports SPI types and `runCap` from `@watchdog/caps/sdk` and the catalog from `@watchdog/caps`. Inside this package import the SDK by relative path (`../../sdk`): Vite does not resolve package self-references.
- A Cap's `run` needs `HttpClient | Egress` (`CapServices`): DNS, TLS and model calls use `yield* Egress` (`resolve`, `tlsConnect`, `llmFetchFor`), never a resolver or socket. A test that asserts a Cap's recorded calls uses `createRecordedRun` (`src/testing`).
- `runCap` is the Promise edge for `run()` tests (it provides `toolsHttpClientLayer`; a sanctioned edge in `effectRunEdges`, `oxlint.config.ts`). Job collect yields `cap.run(ctx)` directly. `itRunsCollectCap` (`src/testing`) covers the thin Collect Caps; harvest, extract.ai, url.enrich, file.analyze, and eml.analyze have dedicated `run.test.ts`.
- Layout: one folder per Cap id, dots → path segments (`network/dns.lookup/{cap,interpret,input}.ts`); shared helpers in `evidence/lib/` (Process) and `lib/collect/` (Collect, `defineCollectCap`). Collect `input.ts` seeds use the `@watchdog/schemas` `*SeedSchema` helpers, not bare `requiredText`; seeds normalize at parse time, and `toCapDescriptor(def, version)` (the catalog) and `toCapMetadata(def)` (no version, for callers that read a Cap's declared metadata) must emit JSON Schema from the input shape so `pnpm generate:caps` stays green.
- Collect interpret emits `validatedIdentifierValue`-normalized identifiers so Collect and Process dedupe the same way (IPv6 canonicalized, related values equal to the query seed dropped). Process interpret throws on malformed ctx ids; Collect returns `INVALID_COLLECT_ENTITY_SUMMARY`.
- Playbooks: `planPlaybook` validates the whole recipe and emits step 0 only; a later step is created once the step before it has settled and the steps it reads succeeded. Bind fills the next Job from the seed, `evidenceIds`, or Cap `handoff` bags (pure `handoff?: (report) => JobHandoff | undefined`, persisted by core on success including cache hits). Fan-out inserts capped sibling Jobs (`playbookFanIndex`); an empty fan-out completes its step and the run goes on. `decidePlaybookAdvance` never abandons: a step whose bind or fan-out sources (`playbookStepDependencies`, transitive) ended without success is skipped, a bind or fan-out error counts as that step failing, and the run finishes with an `outcome` (`succeeded | partial | failed`) when no step can run; `playbookStepViews` is the pure per-step view (skipped is derived, never stored). Do not fold harvest + extract.ai or act Caps into default books.
- Breach corpus (D5): DeHashed and Snusbase take `ctx.breachCredentialMode` (`safe` or `full`) and `ctx.credentialFingerprint` and pass them to the tools fetch (`credentials` option, required); `safe` stores no plaintext password or hash in any artifact (attributes and a keyed fingerprint only), `full` stores them as before. The key behind the fingerprint stays in core: never ask for it, never add a second way to hash a credential. A Claim never quotes a credential (`describeCredential`), and never `ctx.log` one. A new `breach.*` Cap needs an entry in `breach/export-redaction.ts` (`credential-modes.test.ts` fails without one). Watchdog never uses a retrieved credential to log in to anything. HIBP / Hudson Rock stay counts-only because their APIs return no plaintext.
- `breach.leakradar.lookup` is masked search only. The client (`packages/tools/src/breach/leakradar.ts`) has exactly three routes (`POST /search/email`, `GET /search/domain/{domain}`, `GET /search/domain/{domain}/all`), never sends `auto_unlock`, and has no unlock, export or password-range route (unlocking spends the account's points, and the terms bar redistribution, derivative datasets, contacting breach victims and high-volume extraction). A response is read through an allowlist (masked username only if it contains `*`, source URL reduced to its host, dates, counts, `unlocked`, category) and the strict snapshot schema rejects any other key, so a `password`, plaintext `username` or leak `id` never reaches Evidence. One page per run (`pageSize` at most 100, `page` at most 10, `isTruncated`). A domain's summary (`total`, category counts, possibly an estimate) and its listing (`listingTotal`, which drives paging) are separate statements in the snapshot and the Claim, never merged. A 429 is retried once only when `Retry-After` is at most 5 s (`retry: false` turns the shared retry off), else `RateLimitedError`; 401 and 402/403 are fixed-message `ValidationVendorError`s, 503 and 400/422 stay `HttpVendorError`. Tests: `packages/tools/src/breach/__tests__/leakradar.test.ts`, `leakradar.lookup/__tests__/`.
- DNS/WHOIS Collect Caps call `normalizeHost` before resolving.
- `CapContext.caseId` is a `CaseId` (ADR-0003) and `evidenceSnapshot.caseId` is branded through `evidenceSnapshotSchema`; test harnesses build them with `testCaseId` from `@watchdog/schemas/testing`, never a cast.
- `tsconfig.json` extends the root `tsconfig.base.json` (Node types, no JSX) and excludes tests like every package; `tsconfig.test.json` adds them. It no longer extends `apps/web/tsconfig.json` (enforced by `scripts/__tests__/tsconfig-base.gate.test.ts`).
- Vault slots (`known-credentials.ts`) are secrets unless the entry says `secret: false` (a base URL such as `AI_COMPAT_BASE_URL`): core registers each secret value a Cap reads with the Job's provider-call ledger, so recorded URLs show it as `[credential:NAME]` (`isSecretCredential`; see [`caps-boundary`](../../docs/reference/platform/caps-boundary.md#outbound-http)). A new config-only slot sets `secret: false`.
